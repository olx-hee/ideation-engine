## 1. 무슨 문제를 푸나

팀으로 아이디어 회의를 하면 흔히 이렇게 됩니다.

- 서로 눈치만 보다가 **목소리 큰 한 사람**이 방향을 정해 버린다.
- 다들 비슷한 아이디어만 내서 **다양성이 안 나온다.**
- 열심히 회의했는데 **결과가 정리되지 않고** 흩어진다.

IdeationEngine은 이 세 가지를 **판을 짜서** 해결합니다.
"자유롭게 얘기해 보세요"가 아니라, 각자에게 **다른 출발점**을 주고,
**정해진 단계**(워밍업 → 발산 → 분석·투표 → 보고서)로 이끌고,
마지막에 **결과를 자동으로 묶어** 줍니다.

## 2. 핵심 아이디어 세 가지

> ⚠️ **최종 제품(핸드오프 패키지)에는 이 중 ①만 채택됐습니다.** ②·③은 개발 초기 React 프로토타입에서
> 검증해 봤던 아이디어인데, 최종 스펙은 해커톤·공모전 팀을 위해 **오프라인 전용**·**AI 인터뷰 → 자유 발산 →
> 투표 → 파트 나누기 하나의 고정 흐름**으로 범위를 좁혔습니다. 근거: `IdeationEngine-개발핸드오프/screens/01-landing`
> (태그라인 "오프라인 아이디어 세션"), `04-session-create`(시간·인원만 설정, 방식 선택 없음) — 최종 스펙 어디에도
> SCAMPER·6색 모자·온라인 모드 문구는 없습니다. ②·③은 아래에 "검증했지만 최종에는 없음"으로 표시합니다.

**① 사람마다 '다른 각도'에서 출발시킨다** — ✅ 최종 제품에 있음
같은 질문을 모두에게 던지면 답이 비슷해집니다. 그래서 참여자의 **역량(프로필)**을 보고
비즈니스 · 사용자경험 · 기술 · 혁신 같은 **서로 다른 각도**를 나눠 줍니다.
→ 아이디어가 구조적으로 겹치지 않게 됩니다. (프로필 화면에 "AI가 각도 배분의 참고 맥락으로 씁니다"로 명세돼 있음)

**② 상황에 맞는 '진행 방식'을 고른다** — 🧪 프로토타입에서 검증, 최종 제품에는 없음
목표에 따라 회의 방식이 달라야 한다는 가정으로, 프로토타입 단계에서 세 가지를 만들어 실제로 화면이
바뀌는지까지 검증했습니다.
- **자유 브레인스토밍** — 넓게 많이 쏟아낼 때
- **SCAMPER** — 기존 것을 개선·변형할 때 (7개 렌즈로 비틀기)
- **Six Thinking Hats(6색 모자)** — 여러 관점을 균형 있게 검토·결정할 때

최종 제품은 해커톤·공모전 팀이라는 타겟에 맞춰 **"AI 인터뷰 → 자유 발산" 고정 흐름 하나**로 범위를 좁혔습니다.

**③ '오프라인/온라인' 진행을 나눈다** — 🧪 프로토타입에서 검증, 최종은 오프라인으로 확정
- **오프라인 모드** — 해커톤처럼 다 같이 모여서, 공유 타이머로 함께 진행 (**최종 제품이 채택한 방향**)
- **온라인 모드** — 팀플처럼 각자 편한 시간에, 링크로 참여 (최종 제품에는 없음)

## 4. 기능별 설명 — 무엇을 / 왜 / 무슨 역할

아래는 **최종 제품(핸드오프 패키지, 화면 36개)** 기준 설명입니다. 화면·API 스펙은 확정됐고,
실제 백엔드 서버 구현은 진행 중입니다(§6 참고).

### 계정 · 입장 (회원가입 · 로그인 · 방 코드)
- **왜:** 게스트 입장을 허용하면 익명 댓글·투표의 신뢰가 깨지고, 나중에 인증을 붙이기도 어렵다.
- **역할:** 이메일/소셜 회원가입 → 로그인(액세스 토큰 1시간 + 리프레시 쿠키 30일) → 프로필 작성까지
  끝나야 세션을 만들거나 들어갈 수 있다. **방 코드(대문자·숫자 6자리)** 로 입장, 별도 초대 토큰 없이
  코드로 재접속도 가능하다.

### 프로필 기반 '각도' 배분
- **왜:** 발산의 다양성을 사람 성향에 맡기지 않고 **구조로 보장**하려고.
- **역할:** 프로필의 역량을 비즈니스·사용자경험·기술·혁신 같은 각도로 매핑하고, 팀 전체가 한 각도에
  몰리지 않게 분산 배정한다(AI가 배분의 참고 맥락으로 씀). 각자 "자기 각도"에서 아이디어를 시작한다.

### 아이스브레이킹 → 발산 → 투표 (고정 흐름)
- **왜:** "자유롭게 얘기해 보세요"보다 **정해진 단계**가 다양성과 결과 정리를 둘 다 보장한다.
- **역할:** AI 인터뷰 질문 5개(+최근 소식 카드) → 재료 뽑기·묶기 → 각자 아이디어 작성/AI 추천에서
  고르기 → 익명 순위표·익명 댓글 → AI 검증·현실성 체크 → **1인 2표 투표** → 진행자가 주제 확정.

### 파트 나누기 (주제 확정 이후)
- **왜:** 아이디어를 정했어도 "누가 뭘 맡을지"가 또 다른 회의거리가 된다.
- **역할:** 팀 스킬(이름 없이 인원 수만 AI에 전달)로 파트·후보를 자동 추천하고, 후보가 겹친 사람에게만
  추가 질문을 던져 팀장이 최종 배치를 확정한다. 마지막에 **A4 2쪽 보고서**로 정리된다.

### AI 작업 15개 — 작업마다 다른 무게의 AI
- **왜:** 인터뷰 꼬리질문처럼 즉시 답해야 하는 것과, 보고서 생성처럼 시간이 걸려도 되는 것을 같은
  방식으로 부르면 느리거나 비싸진다.
- **역할:** [`docs/05-AI-작업-목록.md`](IdeationEngine-개발핸드오프/docs/05-AI-작업-목록.md)에 15개 작업을
  가벼운/중간/무거운 세 무게로 나눠 정의해 뒀다. 이 구분은 아래 React 프로토타입에서 먼저 검증한 결과를
  이어받은 것이다(§5 참고). "지어내지 않기(검색 결과에 없는 사실 금지)"·"이름을 AI에 보내지 않기" 같은
  안전 규칙도 문서에 명시돼 있다.

### 정직성 원칙
- **왜:** 사용료를 받는 서비스라면, 근거 없는 수치를 사실처럼 보여주면 안 된다.
- **역할:** AI 검증 결과는 "참고용"으로 표시하고 등급이 낮아도 투표에서 빼지 않는다. 목업 모드와 실제
  서버 모드를 코드에서 분명히 구분한다(§6).

### AI 코드 검수 협업 (Grok)
- **왜:** 한 명(또는 하나의 AI)이 만든 코드는 사각지대가 생긴다.
- **역할:** 주 개발은 Claude가, **검수·피드백은 Cursor의 Grok**이 맡는 분업.
  검수 이력은 [`grok-검수/`](grok-검수/) 폴더에, 방식은 [REVIEW_GUIDE.md](REVIEW_GUIDE.md)에 있다.

> 🧪 **참고 — React 프로토타입에만 있던 것 (최종 제품에는 없음):** 오프라인/온라인 모드 분리,
> 아이데이션 방식 3종(자유·SCAMPER·6색 모자) 선택. §2 참고.

## 5. 심사 포인트 — 창의성 · 사업성 · 보안

이 프로젝트는 심사를 받습니다. 심사의 **창의성**과 **사업성** 기준을 정면으로 겨냥한 우리 차별점입니다.
(정직하게: 아래 각 항목에 **구현 완료 / 설계·진행 중**을 표기합니다 — 정직성도 우리 원칙입니다.)

> ⚠️ **정직하게 짚어둘 것 — 아래 표는 최종 제품에 "지금 돌고 있는" 것이 아니라, React 프로토타입으로
> 먼저 실측·검증한 결과입니다.** 최종 제품(핸드오프 패키지)의 백엔드는 아직 구현 전이고, 완성되면 이
> 검증 결과를 참고해 만들어질 예정입니다. 또한 최종 제품은 AI 작업을 15개로 더 잘게 나눠 정의했는데
> (핸드오프 패키지의 `docs/05-AI-작업-목록.md`), 15개 기준으로 어떤 모델이 좋을지도 다시 재측정해 뒀습니다
> ([docs/모델선정-테스트기록.md](docs/모델선정-테스트기록.md) 0-2절). 발표할 때 "이 표가 곧 시연 화면에서
> 도는 모델"이라고 말하지 않도록 주의 — **"검증은 끝났고, 구현은 이 검증대로 진행 중"**이 정확한 표현입니다.

### 🎨 창의성 — 일마다 '그 일을 가장 잘하는 AI'를 따로 씁니다

세상에는 여러 회사가 만든 AI가 많습니다 (챗GPT, 클로드, 제미나이, 그리고 잘 안 알려졌지만 성능 좋은 것들).
보통 서비스는 그중 **유명한 하나**만 씁니다. 우리는 이렇게 생각했어요 —
> **"일마다 잘하는 AI가 다르다면, 일에 맞는 AI를 골라 쓰면 결과도 더 좋고 비용도 더 싸지 않을까?"**

**그래서 '어떻게' 확인했는지 — 편애 없이 공정하게:**
- 같은 일(예: 아이디어들을 주제별로 묶어 정리하기)을 **여러 AI에게 똑같이** 시켰습니다.
- 채점할 때 **어느 답을 어느 AI가 만들었는지 가렸습니다.** 유명하다고 봐주는 편애를 막으려고요 — 이름을 가린 블라인드 시험처럼요.
- **한 주제만이 아니라 여러 주제로 반복**했습니다. 한 번 잘한 건 우연일 수 있으니까요.
- 채점은 **또 다른 AI 여러 개**가 하고, 거기에 **자동으로 계산하는 수치**(예: 나온 아이디어들이 서로 얼마나 다른지)도 함께 봤습니다. 한쪽으로 치우치지 않게요.
- **가장 비싸고 유명한 최고급 AI들(클로드·챗GPT 최신판 등)도 같은 대결에 넣어** 공정하게 비교했습니다.
- 마지막으로, 우리가 결과를 **과장하지 않았는지 다른 AI(Grok)에게 교차 검수**까지 받았습니다.

**그렇게 수십 번 비교해서 알게 된 것:**
- **일마다 잘하는 AI가 정말 달랐습니다.** 키워드 뽑기, 아이디어 내기, 정리하기, 검토하기 — 각각 1등이 다르더군요.
- **"여러 AI를 섞어 자동으로 하나로 합치면 더 창의적일 것"은 틀렸습니다.** 오히려 뻔하고 밋밋해졌어요.
  → 창의적인 결과는 **여러 AI가 각자 아이디어를 내고, 그중에서 사람이 고를 때** 가장 좋았습니다.
- **검토(사실 확인)는 아이디어를 만든 AI가 아니라 '다른 AI'가 해야** 실수를 더 잘 잡았습니다.
  (사람도 자기가 쓴 글의 오타는 잘 못 보죠. AI도 똑같습니다.)
- **가장 놀라운 점:** 우리가 고른 **값싼 AI가, 수백 배 비싼 최고급 AI(클로드·챗GPT 최신판 등)를 이기거나 대등**했습니다.
  → "싸다고 나쁜 게 아니다"를 실제 대결로 확인했고, **오픈소스 도구로 재현까지** 해뒀습니다(아래 🔬).

**그래서 최종적으로 일을 이렇게 나눠 맡깁니다:**

| 이 작업은 | 이 AI에게 | 왜 |
|-----------|-----------|----|
| 짧은 키워드 뽑기 | Gemini Flash-Lite | 가볍고 값싼 일에 딱 맞아서 |
| 아이디어 쏟아내기 | Solar | 혼자서도 다양하게 잘 내서 |
| 여러 갈래 컨셉 만들기 | **AI 4개가 각자 하나씩** | 서로 다른 색으로 나와야 팀이 고르기 좋아서 |
| 아이디어 정리·묶기 | Solar | '정리' 시험에서 1등이라서 |
| 보고서·로드맵 쓰기 | DeepSeek | '보고서' 시험에서 1등이라서 |
| 결과 검토·오류 잡기 | Llama (만든 AI와 **다른** 것) | 남이 봐야 실수를 잡으니까 |
| 아이디어 현실성 검토 | DeepSeek | 실현가능성·수요를 냉정하게 따져서 |
| **"이거 이미 있나?" 시중검색** | **Brave 검색** + AI 판정 | **검색은 검색엔진이**, 판정은 AI가 |

**🧭 이게 우리 정체성입니다 — "AI를 각자 잘하는 일에" (많이 쓰는 게 아니라)**
- 우리 서비스의 핵심은 "유명한 AI 하나"도, "여러 AI를 마구 섞기"도 아니라 — **일마다 측정으로 고른 딱 맞는 모델·도구 하나**를 씁니다.
  심지어 "이미 있는 서비스인지" 확인은 **AI가 아니라 검색엔진(Brave)**에게 맡깁니다. (검색은 검색이 잘하니까)
- 그래서 한 번의 회의에 **작업에 따라 여러 모델 + 검색이 각자 역할**로 참여합니다. → *"결국 유명한 AI 하나 래퍼 아니냐"*에 대한 답.
- **정직하게, 기대했다 빗나간 것도 있습니다:** "여러 AI를 자동으로 섞으면 더 창의적"은 우리가 직접 재보니 **틀렸습니다.**
  그래서 우리는 **섞지 않고, 작업마다 측정으로 이긴 것만** 씁니다. (자료조사용 Brave 검색은 붙였고, 슬라이드용 Gamma 등은 아직 확장 과제)
- 우리가 어떤 실험을 했고 결과가 어땠는지 자세한 이야기는 📄 [**docs/모델선정-테스트기록.md**](docs/모델선정-테스트기록.md)에 있습니다.
- 상태: ✅ 위 배분 + 현실성 검토·시중검색까지 **React 프로토타입으로 백엔드 구현·동작 확인(실측 완료)**
  / 🔄 **최종 제품(핸드오프 패키지) 백엔드 구현은 진행 중** — 이 검증 결과를 참고해서 만들어질 예정.
- **솔직한 한계 (부풀리지 않으려고):**
  - **"여러 모델을 써서 더 창의적"이라고 주장하지 않습니다** — 강점은 "많이"가 아니라 "**적재적소·저비용**". 위 표는 *역할 카탈로그*이지, 매 회의에 항상 전부 호출한다는 뜻이 아닙니다(작업에 걸린 것만 부름).
  - "이미 있나" 검색은 **진짜 URL 근거**지만 **최종 라벨은 AI 판정**이고, 검증 표본이 아직 작습니다. (Brave 키가 없으면 검색 게이트는 꺼집니다.)
  - 현실성 검토의 "왜 아직 없나·수요"는 아직 **AI 추정 + 검색 보강**(완전 실측은 아님).
  - "어떤 아이디어가 더 창의적인가"는 사람 평가가 더 필요합니다(현재 소표본, 게이트 적용 후 재측정은 아직 안 함).

### 💰 사업성 ① — 쉬운 일엔 값싼 AI, 어려운 일엔 좋은 AI → 비용 절감

- 보통 앱은 **쉬운 일이든 어려운 일이든 비싼 AI 하나**로 다 처리합니다. 낭비죠.
  (실은 지금 우리가 Claude·Cursor를 쓰는 방식이 딱 그렇습니다.)
- 우리는 **일의 종류에 따라 값싼 AI와 좋은 AI를 나눠** 씁니다. 회의가 이미
  [아이스브레이킹 → 아이디어 → 분석 → 보고서] 단계로 나뉘어 있어서, **단계마다 어떤 AI를 쓸지 미리 정해두면** 됩니다.
  (예: 짧은 키워드 뽑기는 값싼 AI / 분석·보고서는 좋은 AI)
  → 나중에는 "해커톤 준비해줘" 같은 자유로운 요청도 **알아서 잘게 쪼개** 배분할 계획입니다. (다음 단계)

- **아낀 돈을 '정직하게' 보여주려고 규칙을 정해뒀습니다** — 카페 영수증처럼 생각하면 쉽습니다:
  1. **영수증처럼 다 적기.** AI를 한 번 부를 때마다 "무슨 일에 · 어떤 AI로 · 얼마" 썼는지 기록합니다.
     이때 **'실제 작업에 든 돈'과 '어떤 AI를 쓸지 고르고 결과를 검토하는 데 든 돈'을 나눠** 적어서, 눈에 잘 안 띄는 비용까지 다 보이게 합니다.
  2. **"이만큼 아꼈다"를 정직하게 계산.** 회의 한 번에 든 돈을 두 가지로 비교합니다 —
     **"값싼 AI를 섞어 써서 실제로 낸 돈" vs "만약 전부 비싼 AI로 했다면 냈을 돈".** 단, 뒤엣것은 **실제로 안 써본 '가정'**이라고 화면에 분명히 적습니다. (안 낸 돈을 낸 것처럼 부풀리지 않으려고요.)
  3. **싼 것만 자랑하지 않기.** "쌌다"만 크게 보여주면 오해를 부르니, **"그래서 품질이 나빠지진 않았나"**를 바로 옆에 같이 보여줍니다.
  4. **"지금 공짜"와 "계속 공짜"를 구분.** 일부 AI는 지금은 무료지만 **나중에 유료가 될 수 있어서**, 무료로 아낀 금액은 "이게 영원히 공짜라는 뜻은 아님"이라고 따로 표시합니다. (사업 계획의 돈 계산을 부풀리지 않으려고요.)

- 상태: ✅ **일에 맞게 AI를 나눠 보내는 방식을 React 프로토타입으로 구현해 실제로 돌려봤고**, 어떤 AI가
  얼마나 싼지 **실제로** 재봤습니다. 쉬운 일을 값싼 AI에게 보내니 **최고급 AI 하나만 쓰는 것보다 약 99.8% 저렴**
  한데도 품질은 대등했고, 이 절감을 오픈소스 도구로 외부 실측했습니다 (바로 아래 🔬).
  🔄 **최종 제품 백엔드에는 아직 구현되지 않았고**, 이 검증 결과(모델 선정)를 참고해서 구현될 예정입니다.
  ([docs/모델선정-테스트기록.md](docs/모델선정-테스트기록.md))

### 🔬 "우리끼리 계산 아님" — 외부 오픈소스 도구로 검증했습니다

"싸다"·"좋다"를 우리가 스스로 계산하면 *"유리하게 잰 거 아냐?"* 소리가 나올 수 있어서, **바깥의 오픈소스 도구**로 다시 확인했습니다.

**① 비용 — [Langfuse](https://github.com/langfuse/langfuse)(오픈소스 관측 도구)로 실측**
- AI를 부를 때마다 **실제 청구액을 Langfuse가 독립적으로 기록**합니다.
- 같은 작업(발산·분석·보고·컨셉)을 **우리 모델과 최고급 Claude-Opus로 둘 다 진짜 돌려** 비교:
  **우리 $0.0005 vs Opus $0.331 → 약 99.8% 저렴** (가정이 아니라 둘 다 실제로 돌린 값).
- Langfuse가 찍은 합계가 우리 계산과 정확히 일치 → 외부 원장이 뒷받침. *(Langfuse 무료 한도 내라 비용 0)*

**② 품질 — [promptfoo](https://github.com/promptfoo/promptfoo)(오픈소스 평가 도구)로 재현 확인**
- 정리·분석·검토 같은 **객관 작업**을, 우리 모델 vs Opus로 놓고 **제3의 심판 AI**(우리도 Opus도 아닌 중립 모델)가 채점.
- 결과: **분석 0.95 vs 0.90 · 보고 0.95 = 0.95 · 검토 1.0 = 1.0** → **우리 저가 모델이 최고급과 동급(살짝 앞서기도).**
- 설정·결과를 [`eval/`](eval/)에 저장 → 누구나 `npx promptfoo eval`로 재현 가능.

**정직한 한계:** 품질 점수가 천장(0.9~1.0)에 몰려 0.05차는 노이즈 → "명확히 낫다"가 아니라 **"동급"**입니다. 심판도 결국 AI라 **객관 작업엔 믿을 만하지만, "어떤 아이디어가 더 창의적인가"는 사람이 채점해야** 합니다(다음 숙제).

### 🔒 사업성 ② — "돈을 뺏기지 않는 것"도 사업성 (보안)
돈을 버는 것만 사업성이 아니라 **돈을 지키는 것**도 사업성입니다. 우리 서비스의 핵심은 **API LLM**이라,
**API 키 유출·남용 = 곧 금전 피해**입니다.

**최종 제품(핸드오프 패키지) 스펙에 이미 설계돼 있는 것:**
- **게스트 입장 없음** — 회원가입 → 로그인 → 프로필 작성이 끝나야 세션 생성/입장 가능
- **로그인 유지 방식** — 액세스 토큰(1시간, 짧은 수명) + 리프레시는 쿠키(로그인 유지 체크 시 30일)
- **방 코드 = 대문자·숫자 6자리** (초대 토큰 별도 없음 — 단, 아래 한계 참고)
- 상태: 🔄 **설계 완료, 실제 서버 구현은 백엔드가 진행 중** (핸드오프 패키지의 `docs/02-API-공통-규칙.md`)

**아직 스펙에 명시 안 된 것 / 구현 시 반드시 챙길 것:**
| 위협 | 최종 제품에서 필요한 것 | 상태 |
|------|-----------|------|
| **방 코드 무차별 시도(enumeration)** | 6자리 코드는 로그인된 사용자만 시도 가능하지만, 시도 횟수 제한(rate limit)이 스펙에 명시 안 됨 | 🔄 구현 시 추가 필요 |
| **쿠키/CSRF** | 리프레시 쿠키는 HttpOnly·Secure·SameSite + CSRF 방어가 함께 있어야 함 | 🔄 설계 문서 미작성 |
| **AI·검색 API 남용** | 15개 AI 작업(핸드오프 `docs/05`)·검색 호출에 인당 횟수 제한·일일 쿼터 필요 | 🔄 스펙에 "호출 횟수 제한"은 언급됐으나 구체적 수치 미정 |
| **API 키 노출** | 키는 서버 env에만 두고 프론트·번들·레포에 절대 노출하지 않기 | 🔄 백엔드 구현 시 지켜야 함(원칙만 있음) |

**React 프로토타입에서 검증해 둔 패턴 (참고용 — 백엔드 구현 시 재사용 가능):**
프로토타입(`server/`)에서는 API 키 서버 전용 보관, Mongo `$set` 강제(연산자 주입 차단), PATCH allowlist,
helmet(CSP·HSTS), body size 제한, 에러 스택 비노출, prod CORS 화이트리스트 강제를 실제로 구현하고
검수까지 거쳤습니다. **최종 제품 코드는 아니지만, 백엔드가 같은 패턴을 그대로 적용할 수 있습니다.**
검수 이력: [`grok-검수/`](grok-검수/)

- 핵심 요지: **보안은 설계(스펙)에 절반, 검증된 구현 패턴에 절반이 이미 있지만, 최종 제품 코드로
  옮기는 작업 자체는 아직 남아 있습니다.** 이 부분을 "이미 다 됐다"고 발표하지 않도록 주의.

검증하기 위해 만들었던 것입니다. 지금도 실행은 되지만, **화면·흐름은 최종 스펙과 다릅니다**(§2 참고).
- ✅ **MongoDB 연동, 세션/콘텐츠 서버 저장·복원, 오프라인·온라인 모드, 방식 3종(자유·SCAMPER·6색 모자)** —
  모두 실제로 구현·동작 확인까지 끝냈지만, 최종 제품 스펙에는 이어지지 않았습니다.
- ✅ **AI를 일마다 다르게 배분하는 로직(백엔드) 구현·실측 완료** — 작업별로 맞는 AI에 보내기 + 여러 AI가
  컨셉 후보 만들기 + 다른 AI가 검토하기가 실제로 동작했고, 비용·품질을 실측했습니다. **이 실측 결과가
  최종 제품의 핸드오프 `docs/05-AI-작업-목록.md`(작업 15개, 무게 3단계)로 이어집니다.** 코드 자체는 최종 제품에
  이식되지 않았고, 백엔드가 이 결과를 참고해 새로 구현합니다.

**아직 예시(목업) — 최종 제품에서 "시연용"으로 표기해야 할 부분:**
- 화면 뒤 실제 서버가 없어서 지금은 전부 `assets/js/mock.js`의 가짜 응답으로 동작
- AI 검증·현실성 등급, 분석 신뢰도·점수 등 **수치**는 백엔드 구현 전까지는 예시

**다음 목표:** 백엔드 1~7차 API 순서대로 구현 → AI 작업 15개 실제 연결 → 실시간 다중 사용자 흐름 확인.
→ 최종 제품 진행 상황은 [`IdeationEngine-개발핸드오프/팀공유-진행현황.md`](IdeationEngine-개발핸드오프/팀공유-진행현황.md),
프로토타입 시절 설계는 [ROADMAP.md](ROADMAP.md)·[ORCHESTRATOR-DESIGN.md](ORCHESTRATOR-DESIGN.md) 참고(역사적 기록).

## 8. 이 저장소를 읽는 법 — 코드가 어디 있나

> 파일이 많아 보이지만, **실제로 돌려볼 수 있는 코드는 `IdeationEngine-개발핸드오프/`(최종 제품)와
> `src/`+`server/`(AI 검증용 프로토타입) 둘뿐**입니다. 나머지는 대부분 실험·기록이라 무시해도 됩니다.

### 8-1. 두 개의 프론트가 있습니다

헷갈리기 쉬운 부분이라 먼저 짚습니다. 이 저장소에는 **서로 다른 목적의 프론트 구현이 두 개** 있는데,
**`IdeationEngine-개발핸드오프/`가 최종 제품**이고, `src/`(React)는 그 전에 AI 방식을 검증하려고
만들었던 프로토타입입니다.

| | 📦 `IdeationEngine-개발핸드오프/` — 최종 제품 | 🧪 `src/` (React) — AI 검증용 프로토타입 |
|---|---|---|
| 목적 | 실제로 낼 **화면 36개 + API 명세**(회원가입·초대·투표·파트나누기·보고서까지) | AI 오케스트레이터·비용 절감 실험을 **먼저 검증**해 본 것 (최종 제품 아님) |
| 기술 | 순수 HTML·CSS·JS (프레임워크 없음) | React + Vite + Tailwind |
| 백엔드 | 명세만 있음(`docs/03` API 74개) — **서버 구현 진행 중** | `server/`(Express) — AI 실호출 코드까지 구현됨(참고용, 최종 제품에 이식 안 됨) |
| 인증 | 회원가입·로그인·소셜 로그인까지 **설계에 포함** | 없음(세션 UUID만 알면 조작 가능) |
| 지금 상태 | Vercel 배포됨(가짜 서버 모드), 백엔드가 이 명세대로 서버를 만드는 중 | `npm run dev:all`로 로컬 실행은 되지만 개발은 종료, 검증 결과만 참고 |
| 이 문서에서 | [`IdeationEngine-개발핸드오프/README.md`](IdeationEngine-개발핸드오프/README.md) · [팀공유-진행현황.md](IdeationEngine-개발핸드오프/팀공유-진행현황.md) | §3~5의 "(참고)"·"🧪" 표시된 부분 |

**왜 두 개인가:** 프로토타입(`src/`)은 "AI를 작업마다 다르게 배분하면 정말 싸지고 품질도 유지되는가"를
**먼저 검증**하려고 만든 것이고, 그 검증이 끝난 뒤 **실제로 낼 제품의 전체 화면·API**를 확정한 것이
핸드오프 패키지입니다. 핸드오프의 AI 작업 명세(`docs/05`, 15개)는 프로토타입의 오케스트레이터(4~5종
kind)보다 더 잘게 나뉘어 있어, 코드가 아니라 **검증 결과(어떤 모델이 좋은지)만** 이어받았습니다(§6 참고).

**🟣 최종 제품 처음이면 이 3개만:**
- `IdeationEngine-개발핸드오프/index.html` — 화면 목록. 브라우저로 열면 36개를 눌러볼 수 있음.
- `IdeationEngine-개발핸드오프/docs/01-백엔드-한눈에-보기.md` — 백엔드 개발자가 제일 먼저 볼 문서.
- `IdeationEngine-개발핸드오프/팀공유-진행현황.md` — 뭘 했고 뭐가 남았는지 요약.

**🧪 프로토타입(참고용) 처음이면 이 3개만:**
- `src/App.jsx` — 화면·회의 흐름 거의 전부 (React). AI 검증 프로토타입의 심장.
- `src/api.js` — 화면이 서버를 부르는 함수 모음.
- `server/` — 백엔드. `index.js`(API 라우트) · `store.js`(저장/DB) · `orchestrator/`(여러 AI 라우팅 + 현실성·시중검색 게이트).

**⚪ 설정 파일 (거의 볼 일 없음):** `index.html` · `vite.config.js` · `tailwind.config.js` · `postcss.config.js` · `.env.example`(환경변수 예시).

**🔵 이 아래는 '실험·연구·기록' — 앱 실행과 무관, 신규 팀원은 무시해도 됩니다:**
- `benchmarks/` · `eval/` · 루트의 `*.mjs`(`langfuse-*`, `top4-*`, `blind-*`) — 어떤 AI를 쓸지 고르려고 돌린 실험·검증 스크립트와 결과.
- `grok-검수/` — 방향·정직성 교차검수 이력(날짜별).
- `docs/` — 설계 문서. 특히 [`docs/설계-결정-기록.md`](docs/설계-결정-기록.md)에 **"왜 이렇게 만들었나"**가 있음.
- `ORCHESTRATOR-DESIGN.md` · `MODEL-ROSTER.md` · `ROADMAP.md` · `SETUP-DB.md` — 설계·로드맵·DB 세팅 참고.

**팁:** `git log`의 커밋 메시지에 기능마다 "왜/무엇을"이 담겨 있어, 맥락이 궁금하면 로그를 읽으면 된다.
