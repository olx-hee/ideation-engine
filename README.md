# IdeationEngine

> 팀 아이디어 회의를 **AI가 진행·정리해 주는** 웹 서비스.
> 흩어지기 쉬운 브레인스토밍을, 구조를 가진 하나의 세션으로 만든다.

이 문서는 **처음 보는 사람(개발 전공이 아니어도)**이 이 프로젝트가 무엇이고,
왜 이렇게 만들었는지, 지금 어디까지 왔는지 이해할 수 있도록 쓰여졌습니다.
앞으로의 방향은 [ROADMAP.md](ROADMAP.md)에 따로 정리했습니다.

> 🧭 **팀원이라면 먼저:** *"어떤 고민을 했고 왜 이 결론을 냈나"*는 [**docs/설계-결정-기록.md**](docs/설계-결정-기록.md)에 정리돼 있습니다.
> (다중 LLM을 왜 버렸는지, 현실성 게이트·사람 시드·AI fallback을 왜 이렇게 정했는지 — 커밋 로그에 안 보이는 '왜'.)

## 1. 무슨 문제를 푸나

팀으로 아이디어 회의를 하면 흔히 이렇게 됩니다.

- 서로 눈치만 보다가 **목소리 큰 한 사람**이 방향을 정해 버린다.
- 다들 비슷한 아이디어만 내서 **다양성이 안 나온다.**
- 열심히 회의했는데 **결과가 정리되지 않고** 흩어진다.

IdeationEngine은 이 세 가지를 **판을 짜서** 해결합니다.
"자유롭게 얘기해 보세요"가 아니라, 각자에게 **다른 출발점**을 주고,
**정해진 단계**(워밍업 → 발산 → 분석·투표 → 보고서)로 이끌고,
마지막에 **결과를 자동으로 묶어** 줍니다.

---

## 2. 핵심 아이디어 세 가지

**① 사람마다 '다른 각도'에서 출발시킨다**
같은 질문을 모두에게 던지면 답이 비슷해집니다. 그래서 참여자의 **역량(프로필)**을 보고
비즈니스 · 사용자경험 · 기술 · 혁신 같은 **서로 다른 각도**를 나눠 줍니다.
→ 아이디어가 구조적으로 겹치지 않게 됩니다.

**② 상황에 맞는 '진행 방식'을 고른다**
목표에 따라 회의 방식이 달라야 합니다. 그래서 세 가지를 제공합니다.
- **자유 브레인스토밍** — 넓게 많이 쏟아낼 때
- **SCAMPER** — 기존 것을 개선·변형할 때 (7개 렌즈로 비틀기)
- **Six Thinking Hats(6색 모자)** — 여러 관점을 균형 있게 검토·결정할 때

**③ '오프라인/온라인' 진행을 나눈다**
- **오프라인 모드** — 해커톤처럼 다 같이 모여서, 공유 타이머로 함께 진행
- **온라인 모드** — 팀플처럼 각자 편한 시간에, 링크로 참여

## 3. 지금 실행해 보기

> Node.js가 설치돼 있어야 합니다. **API 키나 데이터베이스가 없어도 그냥 실행됩니다.**
> (없으면 자동으로 임시 메모리 저장 + AI는 예시 응답으로 동작)

```bash
npm install
npm run dev:all
```

- 화면(프론트): `http://localhost:5173`
- 서버(백엔드): `http://localhost:3001`

프론트만 보려면 `npm run dev`, 서버만 켜려면 `npm run server`.

## 4. 기능별 설명 — 무엇을 / 왜 / 무슨 역할

이 저장소의 커밋은 **기능 단위로 나뉘어** 있습니다(`git log`). 아래는 그 요약입니다.

### 진행 모드 분리 (오프라인 · 온라인)
- **왜:** 해커톤(동시)과 팀플(비동기)은 진행 흐름이 완전히 다르다.
- **역할:** 모드에 따라 "전원 입장해야 시작" vs "링크만 있으면 바로 시작"으로
  대기실·타이머·안내 문구가 갈린다.

### 프로필 기반 '각도' 배분
- **왜:** 발산의 다양성을 사람 성향에 맡기지 않고 **구조로 보장**하려고.
- **역할:** 프로필의 역량을 각도로 매핑하고, 팀 전체가 한 각도에 몰리지 않게
  분산 배정한다. 각자 "자기 각도"에서 아이디어를 시작한다.

### 아이데이션 방식 3종
- **왜:** 목표가 다르면 좋은 회의 방식도 다르다. "무엇을 골라도 똑같은" 가짜 선택이
  아니라 **실제로 화면이 바뀌게** 하려고.
- **역할:** 목표 문장을 분석해 방식을 **추천**하고(근거 없는 가짜 % 대신 규칙 계산),
  선택한 방식이 발산 단계 화면(자유 입력 / 7렌즈 / 6색 모자)을 실제로 바꾼다.

### 방식을 세션 전 단계에 반영
- **왜:** 방식이 발산에서만 바뀌면 세션 전체의 일관성이 떨어진다.
- **역할:** 헤더 배지, 아이스브레이킹·분석·보고서 문구까지 선택한 방식을 관통시킨다.

### 백엔드 API + 세션/콘텐츠 영속화
- **왜:** 새로고침하면 다 날아가고, 여러 기기에서 이어갈 수 없으면 실제 서비스가 못 된다.
- **역할:** 세션(목표·방식·진행단계)과 내 제출물(아이스브레이킹·아이디어·투표)을
  서버에 저장하고 복원한다. **서버가 없거나 죽어도 앱은 그대로 동작**한다(로컬 폴백).

### 정직성 원칙
- **왜:** 사용료를 받는 서비스라면, 근거 없는 수치를 사실처럼 보여주면 안 된다.
- **역할:** 아직 목업인 분석·점수·설문 수치에는 "시연용" 표기를 붙이고,
  근거 없는 가짜 퍼센트는 제거했다. **진짜와 예시를 명확히 구분**한다.

### AI 코드 검수 협업 (Grok)
- **왜:** 한 명(또는 하나의 AI)이 만든 코드는 사각지대가 생긴다.
- **역할:** 주 개발은 Claude가, **검수·피드백은 Cursor의 Grok**이 맡는 분업.
  검수 이력은 [`grok-검수/`](grok-검수/) 폴더에, 방식은 [REVIEW_GUIDE.md](REVIEW_GUIDE.md)에 있다.

## 5. 심사 포인트 — 창의성 · 사업성 · 보안

이 프로젝트는 심사를 받습니다. 심사의 **창의성**과 **사업성** 기준을 정면으로 겨냥한 우리 차별점입니다.
(정직하게: 아래 각 항목에 **구현 완료 / 설계·진행 중**을 표기합니다 — 정직성도 우리 원칙입니다.)

### 🎨 창의성 — 일마다 '그 일을 가장 잘하는 AI'를 따로 씁니다

세상에는 여러 회사가 만든 AI가 많습니다 (챗GPT, 클로드, 제미나이, 그리고 잘 안 알려졌지만 성능 좋은 것들).
보통 서비스는 그중 **유명한 하나**만 씁니다. 우리는 이렇게 생각했어요 —
> **"일마다 잘하는 AI가 다르다면, 일에 맞는 AI를 골라 쓰면 결과도 더 좋고 비용도 더 싸지 않을까?"**

**그래서 '어떻게' 확인했는지 — 편애 없이 공정하게:**
- 같은 일(예: 아이디어들을 주제별로 묶어 정리하기)을 **여러 AI에게 똑같이** 시켰습니다.
- 채점할 때 **어느 답을 어느 AI가 만들었는지 가렸습니다.** 유명하다고 봐주는 편애를 막으려고요 — 이름을 가린 블라인드 시험처럼요.
- **한 주제만이 아니라 여러 주제로 반복**했습니다. 한 번 잘한 건 우연일 수 있으니까요.
- 채점은 **또 다른 AI 여러 개**가 하고, 거기에 **자동으로 계산하는 수치**(예: 나온 아이디어들이 서로 얼마나 다른지)도 함께 봤습니다. 한쪽으로 치우치지 않게요.
- **가장 비싸고 유명한 최고급 AI들(클로드·챗GPT 최신판 등)도 같은 대결에 넣어** 공정하게 비교했습니다.
- 마지막으로, 우리가 결과를 **과장하지 않았는지 다른 AI(Grok)에게 교차 검수**까지 받았습니다.

**그렇게 수십 번 비교해서 알게 된 것:**
- **일마다 잘하는 AI가 정말 달랐습니다.** 키워드 뽑기, 아이디어 내기, 정리하기, 검토하기 — 각각 1등이 다르더군요.
- **"여러 AI를 섞어 자동으로 하나로 합치면 더 창의적일 것"은 틀렸습니다.** 오히려 뻔하고 밋밋해졌어요.
  → 창의적인 결과는 **여러 AI가 각자 아이디어를 내고, 그중에서 사람이 고를 때** 가장 좋았습니다.
- **검토(사실 확인)는 아이디어를 만든 AI가 아니라 '다른 AI'가 해야** 실수를 더 잘 잡았습니다.
  (사람도 자기가 쓴 글의 오타는 잘 못 보죠. AI도 똑같습니다.)
- **가장 놀라운 점:** 우리가 고른 **값싼 AI가, 수백 배 비싼 최고급 AI(클로드·챗GPT 최신판 등)를 이기거나 대등**했습니다.
  → "싸다고 나쁜 게 아니다"를 실제 대결로 확인했고, **오픈소스 도구로 재현까지** 해뒀습니다(아래 🔬).

**그래서 최종적으로 일을 이렇게 나눠 맡깁니다:**

| 이 작업은 | 이 AI에게 | 왜 |
|-----------|-----------|----|
| 짧은 키워드 뽑기 | Gemini Flash-Lite | 가볍고 값싼 일에 딱 맞아서 |
| 아이디어 쏟아내기 | Solar | 혼자서도 다양하게 잘 내서 |
| 여러 갈래 컨셉 만들기 | **AI 4개가 각자 하나씩** | 서로 다른 색으로 나와야 팀이 고르기 좋아서 |
| 아이디어 정리·묶기 | Solar | '정리' 시험에서 1등이라서 |
| 보고서·로드맵 쓰기 | DeepSeek | '보고서' 시험에서 1등이라서 |
| 결과 검토·오류 잡기 | Llama (만든 AI와 **다른** 것) | 남이 봐야 실수를 잡으니까 |
| 아이디어 현실성 검토 | DeepSeek | 실현가능성·수요를 냉정하게 따져서 |
| **"이거 이미 있나?" 시중검색** | **Brave 검색** + AI 판정 | **검색은 검색엔진이**, 판정은 AI가 |

**🧭 이게 우리 정체성입니다 — "AI를 각자 잘하는 일에" (많이 쓰는 게 아니라)**
- 우리 서비스의 핵심은 "유명한 AI 하나"도, "여러 AI를 마구 섞기"도 아니라 — **일마다 측정으로 고른 딱 맞는 모델·도구 하나**를 씁니다.
  심지어 "이미 있는 서비스인지" 확인은 **AI가 아니라 검색엔진(Brave)**에게 맡깁니다. (검색은 검색이 잘하니까)
- 그래서 한 번의 회의에 **작업에 따라 여러 모델 + 검색이 각자 역할**로 참여합니다. → *"결국 유명한 AI 하나 래퍼 아니냐"*에 대한 답.
- **정직하게, 기대했다 빗나간 것도 있습니다:** "여러 AI를 자동으로 섞으면 더 창의적"은 우리가 직접 재보니 **틀렸습니다.**
  그래서 우리는 **섞지 않고, 작업마다 측정으로 이긴 것만** 씁니다. (자료조사용 Brave 검색은 붙였고, 슬라이드용 Gamma 등은 아직 확장 과제)
- 우리가 어떤 실험을 했고 결과가 어땠는지 자세한 이야기는 📄 [**docs/모델선정-테스트기록.md**](docs/모델선정-테스트기록.md)에 있습니다.
- 상태: ✅ 위 배분 + 현실성 검토·시중검색까지 **백엔드 구현·동작 확인** / 🔄 **화면(프론트) 연결은 아직** — 지금 데모 화면은 목업.
- **솔직한 한계 (부풀리지 않으려고):**
  - **"여러 모델을 써서 더 창의적"이라고 주장하지 않습니다** — 강점은 "많이"가 아니라 "**적재적소·저비용**". 위 표는 *역할 카탈로그*이지, 매 회의에 항상 전부 호출한다는 뜻이 아닙니다(작업에 걸린 것만 부름).
  - "이미 있나" 검색은 **진짜 URL 근거**지만 **최종 라벨은 AI 판정**이고, 검증 표본이 아직 작습니다. (Brave 키가 없으면 검색 게이트는 꺼집니다.)
  - 현실성 검토의 "왜 아직 없나·수요"는 아직 **AI 추정 + 검색 보강**(완전 실측은 아님).
  - "어떤 아이디어가 더 창의적인가"는 사람 평가가 더 필요합니다(현재 소표본, 게이트 적용 후 재측정은 아직 안 함).

### 💰 사업성 ① — 쉬운 일엔 값싼 AI, 어려운 일엔 좋은 AI → 비용 절감

- 보통 앱은 **쉬운 일이든 어려운 일이든 비싼 AI 하나**로 다 처리합니다. 낭비죠.
  (실은 지금 우리가 Claude·Cursor를 쓰는 방식이 딱 그렇습니다.)
- 우리는 **일의 종류에 따라 값싼 AI와 좋은 AI를 나눠** 씁니다. 회의가 이미
  [아이스브레이킹 → 아이디어 → 분석 → 보고서] 단계로 나뉘어 있어서, **단계마다 어떤 AI를 쓸지 미리 정해두면** 됩니다.
  (예: 짧은 키워드 뽑기는 값싼 AI / 분석·보고서는 좋은 AI)
  → 나중에는 "해커톤 준비해줘" 같은 자유로운 요청도 **알아서 잘게 쪼개** 배분할 계획입니다. (다음 단계)

- **아낀 돈을 '정직하게' 보여주려고 규칙을 정해뒀습니다** — 카페 영수증처럼 생각하면 쉽습니다:
  1. **영수증처럼 다 적기.** AI를 한 번 부를 때마다 "무슨 일에 · 어떤 AI로 · 얼마" 썼는지 기록합니다.
     이때 **'실제 작업에 든 돈'과 '어떤 AI를 쓸지 고르고 결과를 검토하는 데 든 돈'을 나눠** 적어서, 눈에 잘 안 띄는 비용까지 다 보이게 합니다.
  2. **"이만큼 아꼈다"를 정직하게 계산.** 회의 한 번에 든 돈을 두 가지로 비교합니다 —
     **"값싼 AI를 섞어 써서 실제로 낸 돈" vs "만약 전부 비싼 AI로 했다면 냈을 돈".** 단, 뒤엣것은 **실제로 안 써본 '가정'**이라고 화면에 분명히 적습니다. (안 낸 돈을 낸 것처럼 부풀리지 않으려고요.)
  3. **싼 것만 자랑하지 않기.** "쌌다"만 크게 보여주면 오해를 부르니, **"그래서 품질이 나빠지진 않았나"**를 바로 옆에 같이 보여줍니다.
  4. **"지금 공짜"와 "계속 공짜"를 구분.** 일부 AI는 지금은 무료지만 **나중에 유료가 될 수 있어서**, 무료로 아낀 금액은 "이게 영원히 공짜라는 뜻은 아님"이라고 따로 표시합니다. (사업 계획의 돈 계산을 부풀리지 않으려고요.)

- 상태: ✅ **일에 맞게 AI를 나눠 보내는 부분 구현 완료** + 어떤 AI가 얼마나 싼지 **실제로** 재봤습니다.
  쉬운 일을 값싼 AI에게 보내니 **최고급 AI 하나만 쓰는 것보다 약 99.8% 저렴**한데도 품질은 대등했고, 이 절감을
  오픈소스 도구로 외부 실측했습니다 (바로 아래 🔬). ([docs/모델선정-테스트기록.md](docs/모델선정-테스트기록.md))

### 🔬 "우리끼리 계산 아님" — 외부 오픈소스 도구로 검증했습니다

"싸다"·"좋다"를 우리가 스스로 계산하면 *"유리하게 잰 거 아냐?"* 소리가 나올 수 있어서, **바깥의 오픈소스 도구**로 다시 확인했습니다.

**① 비용 — [Langfuse](https://github.com/langfuse/langfuse)(오픈소스 관측 도구)로 실측**
- AI를 부를 때마다 **실제 청구액을 Langfuse가 독립적으로 기록**합니다.
- 같은 작업(발산·분석·보고·컨셉)을 **우리 모델과 최고급 Claude-Opus로 둘 다 진짜 돌려** 비교:
  **우리 $0.0005 vs Opus $0.331 → 약 99.8% 저렴** (가정이 아니라 둘 다 실제로 돌린 값).
- Langfuse가 찍은 합계가 우리 계산과 정확히 일치 → 외부 원장이 뒷받침. *(Langfuse 무료 한도 내라 비용 0)*

**② 품질 — [promptfoo](https://github.com/promptfoo/promptfoo)(오픈소스 평가 도구)로 재현 확인**
- 정리·분석·검토 같은 **객관 작업**을, 우리 모델 vs Opus로 놓고 **제3의 심판 AI**(우리도 Opus도 아닌 중립 모델)가 채점.
- 결과: **분석 0.95 vs 0.90 · 보고 0.95 = 0.95 · 검토 1.0 = 1.0** → **우리 저가 모델이 최고급과 동급(살짝 앞서기도).**
- 설정·결과를 [`eval/`](eval/)에 저장 → 누구나 `npx promptfoo eval`로 재현 가능.

**정직한 한계:** 품질 점수가 천장(0.9~1.0)에 몰려 0.05차는 노이즈 → "명확히 낫다"가 아니라 **"동급"**입니다. 심판도 결국 AI라 **객관 작업엔 믿을 만하지만, "어떤 아이디어가 더 창의적인가"는 사람이 채점해야** 합니다(다음 숙제).

### 🔒 사업성 ② — "돈을 뺏기지 않는 것"도 사업성 (보안)
돈을 버는 것만 사업성이 아니라 **돈을 지키는 것**도 사업성입니다. 우리 서비스의 핵심은 **API LLM**이라,
**API 키 유출·남용 = 곧 금전 피해**입니다. 그래서 처음부터 보안을 코드에 넣고 **반복 코드 검수**로
다졌습니다. 아래는 **정확한 현재 상태** — ✅완료 / ⚠️부분 / 🔄예정을 구분합니다(정직성).

| 위협 | 우리 방어 | 상태 |
|------|-----------|------|
| **API 키 번들·레포 노출** | 키는 **서버 env에만**. 프론트·번들·저장소에 없음 (`.env` git 제외) | ✅ 완료 |
| **주입(Injection)** | Mongo 업데이트 `$set` 강제(연산자 주입 차단), PATCH allowlist, 신뢰필드 제거 | ✅ 완료 |
| **DOM XSS (HTML 삽입)** | React 텍스트 이스케이프, `dangerouslySetInnerHTML` 미사용, 서버 입력 길이·타입 검증 | ✅ 완료 |
| **서버 하드닝(핵심)** | helmet(CSP·HSTS·X-Frame), body 64kb 제한, 에러 스택 비노출, prod에서 CORS 미설정 시 기동중단·DB 폴백 금지 | ✅ 해당 항목 |
| **AI·콘텐츠 API 남용** | `/api/ai`·콘텐츠 라우트 레이트리밋 | ⚠️ 부분 (sessions 라우트·일일 쿼터 미적용) |
| **CORS** | 프로덕션은 허용 오리진 화이트리스트 강제 | ⚠️ 개발 중엔 요청 오리진 허용(편의) |
| **무인증 뮤테이션** | 세션 UUID를 아는 사람은 조작 가능(capability URL) | 🔄 참가자 인증(B1) 예정 |
| **쿠키/CSRF** | 인증 도입 시 HttpOnly·Secure·SameSite + CSRF 방향 합의됨 | 🔄 예정(설계 문서 미작성) |

- 핵심 요지: **키가 코드·번들에 노출되는 사고는 구조적으로 차단(✅)**. 키 연결 후의
  **호출 남용 방어(인가·일일 쿼터)는 참가자 인증(B1)에서** 마무리합니다. 검수 이력: [`grok-검수/`](grok-검수/)

## 6. 지금 진짜 되는 것 vs 아직 예시(목업)

**실제로 동작:**
- 프로필 → 각도 배분, 목표 기반 방식 추천
- 오프라인/온라인 모드 분리, 세션 타이머
- 방식 3종별 발산 화면
- 세션·내 콘텐츠의 **서버 저장·복원**(새로고침/기기 넘어가도 유지)
- ✅ **MongoDB 데이터베이스 연동 완료** — 세션·아이디어·투표가 실제 DB에 영구 저장됨.
  **서버를 껐다 켜도 데이터가 유지**되는 것까지 검증 완료. (연결법: [SETUP-DB.md](SETUP-DB.md))

- ✅ **AI를 일마다 다르게 배분하는 부분(백엔드) 구현 완료** — 작업별로 맞는 AI에 보내기 +
  여러 AI가 컨셉 후보 만들기 + 다른 AI가 검토하기가 실제로 동작합니다.
  어떤 AI를 쓸지는 실험으로 골랐습니다 ([docs/모델선정-테스트기록.md](docs/모델선정-테스트기록.md)).

**아직 예시(목업) — "시연용"으로 표기됨:**
- 함께 참여하는 **팀원**(지금은 정해진 데모 캐릭터)
- 화면에 보이는 **AI 분석·요약 문구** — 백엔드 오케스트레이터는 실호출이 되지만,
  **프론트 화면 연결은 디자인 작업 후**(현재 UI는 목업 데이터 표시)
- 분석 신뢰도·점수·설문 등 **수치**

**아직 없음(다음 목표):** 병렬 컨셉 선택 UI(백엔드 완료·프론트 연결 예정), 실시간 다중 사용자, 로그인/인증.
→ 자세한 계획은 [ROADMAP.md](ROADMAP.md), 오케스트레이터 설계는 [ORCHESTRATOR-DESIGN.md](ORCHESTRATOR-DESIGN.md).

## 7. 기술 구조 (아주 간단히)

```
[ 브라우저 화면 ]  React + Vite + Tailwind   (src/)
        │  /api 요청
        ▼
[ 서버 ]           Express                    (server/)
        │
        ▼
[ 저장소 ]  MongoDB (✅ 연동 완료) — 없으면 임시 메모리로 폴백   (server/store.js)
[ AI ]      오케스트레이터 (server/orchestrator/) — 작업별 role map 라우팅 + 컨셉 다중 + 독립 검증
            키 있으면 실호출, 없으면 목업 폴백. 모델은 벤치로 선정(docs/모델선정-테스트기록.md)
```

핵심 설계 원칙: **"키·DB 없이도 지금 돌아가되, 환경변수만 넣으면 실서비스가 된다."**
(AI 키는 **서버에만** 두어 화면 코드에 노출되지 않게 함 — 보안 기본)

## 8. 이 저장소를 읽는 법

- `src/App.jsx` — 화면·흐름의 대부분이 여기 있다.
- `src/api.js` — 화면이 서버를 부르는 함수 모음.
- `server/` — 백엔드(`index.js` 라우트, `store.js` 저장, `ai.js` AI 프록시).
- `grok-검수/` — AI 검수 보고서 이력(품질·보안 점검 기록).
- **커밋 메시지**가 기능마다 "왜/무엇을"을 담고 있으니, `git log`를 읽으면 개발 맥락이 보인다.
- `ORCHESTRATOR-DESIGN.md` — 다중 LLM 오케스트레이터 설계(창의성·사업성 핵심).
