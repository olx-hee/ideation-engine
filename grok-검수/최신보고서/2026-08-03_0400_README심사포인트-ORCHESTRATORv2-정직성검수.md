### 1-1. API 키 서버 전용 — 표기 ✅

| 주장 | 코드 사실 | 판정 |
|------|-----------|------|
| 키는 서버에만 | `ANTHROPIC_API_KEY`는 `server/ai.js`의 `process.env`만 참조. `src/`에 `VITE_`/`API_KEY`/`dangerouslySetInnerHTML` 없음 | **주장 자체는 맞음** |

**[Medium] 위협 프레이밍 과장 (표의 ✅와 본문 결합 시)**

→ ✅를 유지하려면 표/각주에 **「번들·레포 비노출 완료 / 호출 인가·쿼터는 B1 예정」**을 분리할 것.  
지금 문장 그대로면 **금전 방어 완료로 오독 가능 → Medium**.

**부수 (Low, README §7 다이어그램):**

### 1-2. XSS / Reflected — 표기 ✅

| 방어 항목 | 코드 | 판정 |
|-----------|------|------|
| React 텍스트 이스케이프 | 사용자 텍스트를 JSX 텍스트로 렌더하는 일반 패턴 | OK |
| `dangerouslySetInnerHTML` 미사용 | `src/` 전수 검색: **0건** | OK |
| 입력 길이·형식 | join/ice/ideas/votes·AI goal/context에 `slice`·타입 가드 | OK (서버측) |

**[Medium] 「Reflected XSS 구현·검증 완료」패키징**  
위협명은 SSR/쿼리스트링 HTML 반사형에 가깝고, 이 앱은 **JSON API + SPA**다.  
실질 방어는 「React 기본 이스케이프 + HTML 삽입 API 미사용 + 길이 제한」이지, Reflected XSS 전용 검증 스위트·프론트 CSP가 아니다.  
`helmet()`은 **Express 응답**에만 적용; Vite가 서빙하는 SPA HTML과는 별개.  
→ ✅를 유지하려면 행 이름을 **「DOM XSS(HTML 삽입)·입력 길이」**로 좁히거나, 상태를 **부분 구현**으로. 현 표기 = **Medium 과장**.

### 1-4. 서버 공격 — 표기 ✅ ← **가장 과장된 셀**

| 세부 주장 | 코드 | 판정 |
|-----------|------|------|
| helmet | `app.use(helmet())` | 있음 (API) |
| body 제한 | `express.json({ limit: "64kb" })` | 있음 |
| 에러 스택 비노출 | 500 → `{ error: "internal error" }`, 미들웨어 400 → `bad request` | 있음 |
| 프로덕션 안전장치 | prod에서 `CORS_ORIGIN` 없으면 `exit(1)`; store측 Mongo 폴백 금지(주석·선행 검수) | 대체로 있음 |
| **레이트리밋** | `contentLimiter` 60/min → join/ice/ideas/votes만; `aiLimiter` 20/min → `/api/ai`만. **sessions POST/GET/PATCH에는 없음** | **전역·전라우트처럼 읽히면 과장** |
| **CORS 화이트리스트** | `CORS_ORIGIN` 있을 때만 배열 화이트리스트. 비프로덕션·미설정 시 `origin: true`(reflect) | **「화이트리스트 완료」는 조건부** |

**[High] 「서버 공격 … ✅ 구현·검증」한 줄 포장**  
여러 방어를 한 셀에 묶고 ✅를 찍으면, 심사자는 **프로덕션급 서버 하드닝 완료**로 읽는다.  
실제는: (1) 레이트리밋 부분 적용, (2) CORS는 prod+env일 때만 fail-closed, (3) 인증 없음으로 세션 UUID 알면 뮤테이션 가능(B1).  
→ 이 셀만으로도 **High급 과장 위험**. 권고 표기 예:

| 위협 | 우리 방어 | 상태 |
|------|-----------|------|
| 서버 하드닝(부분) | helmet·body 64kb·에러 비노출·(콘텐츠·AI) 레이트리밋·prod CORS 필수 | ✅ 해당 항목 |
| CORS 기본(dev) | env 없으면 reflect — 개발용 | ⚠️ 개발 한시 |
| 무인증 뮤테이션 | UUID=capability | 🔄 B1 |

또는 현 셀을 유지하되 각주를 **「레이트리밋=콘텐츠·AI만 / CORS=prod·env 필수」**로 고정.

## 2. 사업성① 「난이도 분류 → 토큰 절감」× ORCHESTRATOR v2 정직성

### 2-1. 측정 방법 4줄 vs §5

| README 측정 | ORCHESTRATOR §5 | 일치 |
|-------------|-----------------|------|
| 호출 로깅 `{용도, 모델, 티어, 토큰, 추정비용}` | `{ purpose, role, model, tier, usageTokens…, estCost }` | **대체로 OK** (README에 `purpose` 세분·usage 진실 출처는 약함) |
| `$Y` 가상 비교 UI 명시 | 베이스라인 가상 비교 체크리스트 | **일치 (좋음)** |
| 승격률·스키마 통과율 병기 | escalate_rate·스키마 실패율 | **일치** |
| 골든 세션 픽스처 | §7 골든 ≥10 | **일치** |

**README에 아직 안 옮겨진 §5 핵심 (심사 허점 후보):**

1. **오버헤드 분리** — `route|escalate|verify|repair`를 절감 분자·분모에 어떻게 넣는지 README 측정에 없음 → 캐스케이드 도입 시 “숨은 이중과금” 반박에 취약.  
2. **목업 단가 vs 실측 배지** — P1은 추정인데 README는 “측정 구조(P1) 착수”만. 데모 숫자를 실측처럼 말하면 위반.  
3. **캐시 절감 분리** — README 침묵.  
4. **무료 티어 $0 영구 가정 금지** — 창의성에서 Nemotron/무료 모델을 강조하므로, 사업성 숫자와 **분리 고지**가 README에 없으면 허점.

→ 측정 서술만 보면 **가상 비교·품질 지표는 정직**. 오버헤드·무료티어·목업배지는 **README 쪽에서 빈칸 → Medium(문서 간 불일치/누락)**.

### 2-2. 「난이도 분류」워딩 vs v2 §4 — **심사 반박 핵심**

| README (사업성①) | ORCHESTRATOR v2 |
|------------------|-----------------|
| 「요청을 **내부 기준으로 난이도 분류**해서 자동 배분」 | 「**P1~P2는 난이도 판단이 필요 없다. 정적 `kind` 표가 곧 답.**」 |
| 예: 자료조사·팀원 능력 / 아이디어 발산·로드맵 | 실제 kind: ice / idea / analyze / report … |
| 분류기·캐스케이드 | **B·P4** (P1에서 반쯤 구현 금지) |

**[Medium→발표 시 High로 승격 가능]**  
심사자가 「분류기는 어디?」라고 물으면, 설계 문서와 README가 **서로 다른 제품**을 말하는 것처럼 보인다.  
권고 문장(정직):

> P1: 세션 단계(`kind`)별 **고정 티어 표**로 저가/고가 배분(이미 분해된 파이프라인).  
> 임의 요청의 **실시간 난이도 분류기**는 P4(경로 B).

예시도 제품 kind에 맞출 것(아이스 키워드 카드=저가, 분석·보고서=고가 등).

### 2-3. 창의성·상태 표기
