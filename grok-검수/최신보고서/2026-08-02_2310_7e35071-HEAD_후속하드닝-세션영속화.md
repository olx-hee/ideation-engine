## 2. [2] 세션 영속화 (`c9143e9`) — 동작 요약

- 생성: `POST /api/sessions` → `ie_sid` + 초대 링크에 실 UUID  
- 로드: `sessionId` 있으면 `GET`으로 data 필드 병합  
- 단계: `PATCH { phase }` best-effort  
- 실패 시 로컬 계속 · 목업 팀원 유지  

### 6차 Question “연동 시 서버가 truth인가?”에 대한 답

| 데이터 | 실제 SoT | 판정 |
|--------|----------|------|
| goal, mins, mode, method, deadlineAt | 서버(GET 성공 시 로컬 덮어씀) | **서버 truth** |
| phase | 로컬 `ie_step` (+ PATCH는 best-effort 기록) | **로컬 truth** — GET이 phase 미적용 |
| votes / ice / ideas UI | 여전히 로컬·목업 | 서버 미연동 |

→ 질문에 대한 설계 답은 **“세션 메타는 서버, 진행도·콘텐츠는 아직 로컬”** 이 정직하다. 주석의 “서버가 source of truth”는 **과장**이며, phase까지 SoT로 가려면 로드 시 `s.phase` → step 반영(및 충돌 규칙)이 필요.

## 3. 발견 목록

### [Medium] `src/App.jsx:936-941` — in-flight `getSession` 미취소 → 세션 전환 시 data 덮어쓰기

· **문제:** `sessionId`가 바뀌거나 `null`이 되어도 이전 `getSession` Promise가 완료되면 `setData`가 그대로 실행된다. 새 세션 로비 중 옛 세션 GET이 늦으면 **goal 등이 이전 세션으로 롤백**될 수 있다.  
· **재현:** 세션 A 생성·로비 → 완료/새 세션으로 빠르게 B 생성. A의 GET이 B의 `setSessionId` 이후에 resolve되면 B 화면에 A 메타가 섞임.  
· **제안:** `AbortController` 또는 `let cancelled`/요청 id 가드; `setSessionId(null)` 시에도 이전 요청 무시.

---

### [Medium] `src/App.jsx:936-941` vs SessionView step — phase SoT 불일치 (진행도 깨짐·주장과 불일치)

· **문제:**  
  1) GET이 `phase`를 적용하지 않음 → 다른 기기/스토리지 초기화 후 서버 phase와 로컬 step 어긋남.  
  2) PATCH 실패 후에도 로컬만 전진 → 서버 phase 정체. 단일 유저·같은 탭에선 `ie_step`으로 버티지만, “서버 영속” 기대와 어긋남.  
· **재현:** step 2까지 진행 중 PATCH 실패(서버 다운) → 서버 phase=0. 다른 브라우저에 `ie_sid`만 넣고 열면(또는 step 스토리지 없음) step 0부터.  
· **제안:** 로드 시 `setStep`/`ie_step`을 `s.phase`로 맞추거나, “메타만 서버 SoT”로 카피/주석 수정. 충돌 시 max(phase) 등 규칙 명시.

---

### [Medium] 보안 — 실 UUID 초대 링크 + 무인증 GET/PATCH (B1 우선순위 상승)

· **문제:** 링크에 찍힌 UUID만 있으면 누구나 세션 조회·phase 조작 가능(기존 API 성질). 연동 전에는 이론, **이제는 공유 가능한 capability URL**. 단일 유저 데모에선 수용 가능하나 상용 경로에선 High/Blocker급.  
· **재현:** 로비 링크 복사 → 타 클라이언트가 `GET/PATCH /api/sessions/:id`.  
· **제안:** 초대 공유 전에 B1(호스트/참가 토큰). 당분간 링크에 “데모·비밀 링크 취급” 고지.

---

### [Low] best-effort와 sessionStorage 이중 기록 — 혼란 여지(치명적 덮어쓰기는 step에선 없음)

· **문제:** GET은 step/votes를 안 건드려 **로컬 진행 중 step을 서버가 잘못 덮지는 않음**(질문에 대한 답: 그 부분은 OK). 대신 서버·로컬 phase가 조용히 어긋날 수 있음.  
· **제안:** 동기화 상태를 UI에 약하게 표시(선택) 또는 phase 양방향 규칙.

---

### [Low] `POST /api/sessions`의 `deadlineAt` — `Number("x") === NaN` 저장 가능

· **문제:** PATCH는 finite 가드가 있는데 create는 `b.deadlineAt ? Number(...)`만. 비정상 값이면 NaN 영속. 정상 프론트는 숫자 전송.  
· **제안:** create에도 `Number.isFinite` 가드.

---

### [Question] create 직후 GET이 mins 클램프 결과로 data를 갱신하는 타이밍

· 의도된 SoT면 OK. 로비에서 깜빡임/값 변화 UX가 거슬리면 create 응답으로 바로 `setData` 맞추고 GET은 새로고침용만.
