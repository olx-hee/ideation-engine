## 0. Claude가 바로 알 것

1. 초기 목표 재도전의 **핵심 장애**는 “다중이 약해서”가 아니라 **창의 축을 LLM-judge 완성도로 재고 있음**.  
2. 해결 = **믿을 측정 스택을 먼저** 만든 뒤, 그 규칙으로만 「다중 > 단일」을 선언.  
3. 사람 축은 **사용자 본인 블라인드 검수만** 한다 (팀원 2차 없음).  
4. 제품/벤치 구현 시 이 프로토콜을 따르고, 옛 완성도 LLM-judge를 **승패 기준으로 쓰지 말 것**.

---

## 1. 문제 정의 (사용자·Grok 합의)

> 다중이 못 이겨서가 아니라, 다중이 이길 법한 지점(**창의성**)을 **못 믿을 자(LLM-judge)** 로 재고 있다.  
> 「다중 > 단일」을 설득력 있게 증명하려면 — 휘어진 자 말고 **객관 다양성 / 사람 평가 / “시중에 있나” 검색 대조**가 먼저.  
> 그게 없으면 어떤 다중 승리도 **흔들리는 축 위의 승리**.

---

## 2. 해결 원칙 — 측정 스택 (3축 + 보조)

**한 숫자로 증명하지 말 것.** 질문을 분리한다.

| 축 | 질문 | 역할 | 승패에 쓸까 |
|----|------|------|-------------|
| **A. 다양성** | 후보가 서로 다른가? | 메아리·과적합·복제 완화 증거 | 보조 또는 필수 조건 중 하나 |
| **B. 사람(본인)** | 해커톤/잠복니즈·걸맞음에 창의한가? | **목표 적합성의 본체** | **필수** |
| **C. 시장 검색** | 시중 유사·수요 힌트? | 잠복/희소·환각 방지 | 보조 또는 필수 조건 중 하나 |
| D. 옛 LLM 완성도 | 유창·구조·한국어? | 회귀 방지·참고만 | **승패에 사용 금지** |

**「다중 승리」선언 조건 (권고, 문서에 고정):**  
- **B(본인 블라인드)에서 이기고**,  
- **A(다양성↑) 또는 C(희소·빈틈↑) 중 하나 이상**.  
- D만 이기면 승리로 **치지 않음**.

---

## 3. 채택 프로토콜 (2차 타인 검수 **제외** 확정판)

사용자가 확정한 흐름:

```
1) 규칙·루브릭 고정
2) 기계 축 먼저 — 다양성(Vendi 등) · 검색 대조 · (선택) AI 초안 태그만
3) 사용자 본인 1차 검수 — 블라인드 S vs M, 루브릭만 체크
4) (제외) 팀원 2차 검수  ← 팀 여건상 제거
5) 불일치 검토 — 주로 AI/기계 축 ↔ 본인 사람 축 어긋난 케이스만 모아 루브릭·프롬프트 보정
```

### 3-1. 단계별 상세

#### (1) 루브릭 고정 (완성도 ❌)
문항 예 (사람 채점용, 미리 문서화):
- “단일 챗(일반 AI 한 방)에 나올 법한가?” → **낮을수록 좋음**
- “일상에서 놓치기 쉬운 불편·잠복 니즈인가?”
- “우리 주제/사람 시드에 걸맞은가?”
- (선택) “이걸로 피치하고 싶다”

승패 규칙 예: 골의 ≥60%에서 M이 S보다 ‘피치/잠복’ 우위 (본인 채점 기준). **실험 전에 문장 고정.**

#### (2) 객관 다양성 (기계)
- 조건 **S(단일)** vs **M(다중·이견 보존·자동종합 없음)**  
- **출력 개수·길이 상한 동일** (안 맞추면 다중만 유리)  
- 지표: **Vendi Score**, 평균 쌍거리(PCD), n-gram 중복(말만 다름 필터)  
- 해석: 다양성↑ = “메아리 감소” 증거. 그 자체로 공모전 품질 승 선언 ❌  

구현: 임베딩 + `vendi-score`(또는 동등 구현) 벤치 스크립트.

#### (3) 「시중에 있나」검색 대조 (기계·역할 LLM 가능)
- 아이디어 → 검색 쿼리 2~3개 생성  
- **실제 검색** (웹/스토어 등) → 유사 0 / 약함 / 많음  
- 이상형 태그: **희소 + 수요 힌트**(불만·니즈 문구). “새로운가?”를 LLM 기억에만 묻지 말 것  
- 결과 스니펫·URL(가능하면) 저장 → 재현·감사

#### (4) 사용자 본인 블라인드 검수 (사람 축 = 여기가 끝)
- 조건 라벨(**S/M**) 가림  
- **기계 점수·AI 창의 태그를 보기 전에** 채점 (오염 방지)  
- 루브릭 문항만 체크, 사후 합리화 최소화  
- 전수 부담 시: **다양성 상위·이견 태그·검색 희소** 케이스 우선

#### (5) 불일치 로그만 (2차 사람 없음)
기록할 패턴 예:
- 기계 다양성↑ / 본인 창의↓ → 산만·말바꾸기  
- AI 완성도↑ / 본인 창의↓ → 유창함 함정 (옛 벤치 병)  
- 검색 희소↑ / 본인 수요↓ → 희귀하지만 쓸모없음  
- 본인 창의↑ / 검색 유사 많음 → “느낌 창의” vs 시장 존재  

이 로그로 루브릭·발산 프롬프트·M 파이프를 보정.

## 4. 2차 타인 검수를 뺀 것에 대한 명시적 한계 (정직성)

Claude·문서·발표 스토리에 **숨기지 말 것:**

| 한계 | 의미 |
|------|------|
| 평가자 n=1 (사용자) | 사람 축은 **설계자 시선**에 가깝다. 팀 일반화·외부 설득력은 2차 있을 때보다 약함 |
| 앵커링·선호 위험 | M을 밀어온 당사자라 **무의식적 편향** 가능 → **블라인드·사전 고정 루브릭·생성/채점 시간 분리**로 완화 |
| “팀원 합의 창의”는 미측정 | 제품이 팀 퍼실리테이션이어도, **현재 벤치의 사람 축은 본인 대리** |

그래도 **옛 LLM-judge만으로 창의 승패를 가르는 것보다는 훨씬 정직**하다.  
나중에 여유 생기면 2차를 선택적으로 복구하면 됨 (프로토콜 자리는 남겨 둠).

---

## 5. 2주 실행 순서 (Grok 권고 → 사용자 채택 범위)

1. **측정기 스모크 (2~3일):** 동일 골 S/M → Vendi+중복만  
2. **루브릭·승패 규칙 문서화 (반나절)**  
3. **본인 미니 벤치 (수일):** 골 5 전후, 블라인드, 기계 숫자 **채점 후** 공개  
4. **검색 대조 MVP** (병렬 가능)  
5. 그다음 **「다중 > 단일」본실험** — 위 선언 조건으로만 승패

*(원 제안의 “팀원 3~5명 사람벤치”는 **본인 단독으로 축소**.)*

## 6. 제품·코드 함의 (북극성과 연결)

선행 `2023` 인계와 합치면:

| 제품 방향 | 측정과의 관계 |
|-----------|----------------|
| 다중 발산 + **이견 보존** (자동종합 ❌) | M 조건의 정의 = 이 파이프 |
| 사람 시드 퍼실리테이션 | 벤치에도 **동일 시드** 넣기 |
| 역할별 LLM (검색·조사·PPT·발산) | **C축 검색**이 곧 조사 롤의 벤치/제품 기능 |
| Self-Refine | 완성도·다듬기 **옵션**; 창의 승패 지표 ❌ |

**하지 말 것:** 새 루브릭을 또 LLM-judge에만 넣어 “창의 점수”로 다중 승리 재증명.

## 7. 대화에서 확정된 사용자 한마디 (원문 취지)

- 측정 스택·본인 확인 후 사람 시선 검수 제안에 대해: **다 좋은데, 팀에서 본인이 감당 → 다른 사람 2차만 빼고 나머지를 Claude에 그대로 전달.**

## 8. Claude 체크리스트

- [ ] 벤치/문서에 승패 = B(본인)+ (A|C), D 제외  
- [ ] S vs M: 이견 보존·무자동종합·출력량 통제  
- [ ] Vendi(또는 동등)+중복 지표 스크립트  
- [ ] 검색 대조: 쿼리·결과 저장 (LLM 기억만으로 “신규” 판정 금지)  
- [ ] 본인 채점 UI/시트: 블라인드, 기계점수 나중 공개  
- [ ] AI↔본인 불일치 로그 필드  
- [ ] 문서에 “사람 평가 n=1” 한계 한 줄  
- [ ] 팀원 2차 검수 구현 **하지 않음** (요청 제외)
