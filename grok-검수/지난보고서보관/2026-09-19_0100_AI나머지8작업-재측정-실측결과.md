## 2. [Blocker] #4 재료 뽑기 — 가벼운 작업 기본값(Flash-Lite)이 개인정보를 못 거른다

- **재현:** "저는 인하대 컴퓨터공학과 3학년 김민준이에요. 자취를 하는데 장 볼 때마다..." 를 Flash-Lite에
  주고 재료를 뽑게 하면, **2번 반복 모두 이름·학교·학과 문장을 avoid=false로 남겼다**(avoidHitPct 0%).
  DeepSeek-V3.2도 0%. 반면 Gemini-2.5-Flash·Mistral-Medium-3는 2번 다 정확히 avoid=true(100%).
- **왜 문제인가:** #4는 15개 작업 중 **한 사람의 인터뷰 원문 전체**를 그대로 AI에 보내는 유일한 자리다.
  다른 작업들은 이미 익명화된 재료·번호만 받지만, #4는 원본을 처음 거르는 단계라 여기서 놓치면
  이름·소속이 재료 목록에 그대로 남아 다음 단계(그룹핑·추천)로 퍼질 수 있다.
- **제안:** ① #4의 모델을 Gemini-2.5-Flash 또는 Mistral-Medium-3로 격상. **하지만 이걸로 충분하다고
  보지 않는다** — 두 모델도 표본이 2회뿐이라 100%를 담보하는 근거는 아니다. ② **정규식/코드 기반
  개인정보 사전 필터**(이름 패턴, "OO대·OO학과" 패턴 등)를 AI 판단 앞에 두고, AI의 avoid는 보조
  수단으로만 쓰는 걸 권장한다. 모델 선택으로 안전을 담보하려 하지 말 것.

## 3. [Medium] #5 재료 묶기 — 클러스터링 품질은 좋은데 스키마가 모델마다 갈림

- **재현:** 9개 재료(3주제: 시간/소통/비용)를 3~5개 그룹으로 묶으라고 하면, **스키마를 통과한 경우엔
  6개 모델 전부 순도(purity) 100%, 커버리지 100%** — 클러스터링 자체는 쉬운 작업이다. 문제는
  **Gemini-2.5-Flash·Llama-3.3이 스키마 자체를 절반만 통과**했다(그룹 개수나 모양이 형식을 벗어남).
  Flash-Lite·Solar-Pro4·DeepSeek-V3.2·Mistral-Medium-3는 100%.
- **제안:** #5는 스키마가 안정적인 네 모델 중 **Flash-Lite(최저가)**를 기본값으로.

## 4. [Low/정보] #6·#9·#2 — 모델을 거의 안 가리는 작업 3개, 가장 싼 모델로 충분

- **#6 아이디어 추천:** 6개 모델 전부 스키마·4개충족·다양성·그라운딩·이름누출없음 = 100%. Flash-Lite도
  최고급 모델과 동일하게 통과.
- **#9 숨은 공통점:** 6개 모델 전부 100% — 심어둔 A+C 교차 연결을 전부 정확히 찾았고, ≤3개 규칙·
  서로 다른 묶음 규칙도 전부 지켰다. 문서가 "중간" 등급을 추천했지만 **Flash-Lite로도 충분**하다
  (0-2에서 #11·#13도 같은 패턴이 나왔던 것과 일치).
- **#2 최근 소식 카드:** 6개 모델 전부 URL 환각 0%·숫자 환각 0%·카테고리 커버 100%. 다만 **지연 차이가
  크다**(Flash-Lite p95 1.9초 vs Llama-3.3 23.1초). 세션 시작 직후 미리 부르는 작업이라 급하진 않지만,
  느리고 비싼 모델을 쓸 이유가 없다 — **Flash-Lite 추천.**

## 5. [Medium] #10·#12 — 측정 방법 자체의 한계를 발견 (모델 결함 아님, 정직하게 기록)

- **#10 인사이트 카드:** "목록으로 쓰지 마라" 체크(문장이 숫자로 시작하면 목록 취급)가 **정상 문장
  "1위 아이디어는..."을 숫자 "1"로 오탐**했다. 원문을 직접 확인하면 6개 모델 전부 한 문단짜리 정상
  문장을 썼다 — **실제 목록화 문제는 없다.** 검사 로직 버그이지 모델 문제가 아니다.
- **#12 겹친 질문:** 형식(선택 4개+서술+예시)은 6개 모델 전부 100%지만, "예시가 주제와 관련 있나"를
  낱말 일치로 검사해서 Gemini-2.5-Flash 0%처럼 낮게 나왔다. 원문을 읽어보면 대부분 **의미상 관련은
  있는데 다른 낱말**(예: "소분·정기배송" 대신 "공동구매·조리키트")을 써서 걸린 경우다. **이 지표는
  하한선으로만 참고할 것** — 사람이 표본을 직접 읽어야 한다.
- **교훈(반복):** `newaxis-report.mjs`(0-2)의 숫자환각 오탐과 같은 종류의 실수다. **자동 판정 스크립트는
  "판정 로직도 검증이 필요한 코드"**라는 걸 다시 확인했다 — 다음 라운드는 초기 실행 후 표본을 사람이
  먼저 훑어보고 판정 로직을 보정하는 단계를 넣는 게 낫다.

## 6. [High] #8 AI가 모은 아이디어 — 방향 결정: "제약 프롬프트 + Solar-Pro4"

0-2 이전부터 걱정했던 지점이다. #8은 정의상 "여러 사람 아이디어를 AI가 합치는" 작업이라, 예전
④번 실험(`모델선정-테스트기록.md` §2④)에서 반증된 "여러 걸 자동으로 섞으면 더 창의적"의 함정에
가장 빠지기 쉬운 자리다. 그래서 모델 비교가 아니라 **프롬프트 전략 A(제약없음) vs B(제약)** 비교를 했다.

| | 전략 A (naive) | 전략 B (constrained) |
|---|---|---|
| 아쉬운점 실제 대응 (평균) | 37.5% | **58.25%** |
| Solar-Pro4 단독 | 0% | **100%** |
| DeepSeek-V3.2 단독 | 33% | 33% (변화 없음) |
| 제목-소스 겹침(자카드) | 0.11 | 0.17 |

- **가장 큰 변화(Solar-Pro4 0%→100%):** 제약을 주니 "구독료 부담을 줄이려고 나눔 게시판에서 재료를
  인증하면 다음 달 구독료를 할인해주는 크레딧 제도"처럼 **원본에 없던 구체적 장치**를 실제로 만들어냈다.
- **주의:** 제목 겹침이 오히려 소폭 올랐는데(0.11→0.17), 이건 "밋밋한 평균화"가 아니라 **"두 소스를
  더 투명하게 결합"**(제목에 둘 다 드러남)으로 보인다 — 자카드 지표만으로는 이 둘을 구분 못 한다.
  샘플을 직접 읽어 확인했다.
- **결정:** #8은 **Solar-Pro4 + 전략 B(제약 프롬프트)**로 간다. 단, 시나리오 1개·3회 반복뿐인 소표본
  실험이고 DeepSeek·Gemini는 제약을 줘도 33%에 머물렀다 — **모델에 따라 효과 차이가 크다.**
  **서버 측에 반드시:** sourceIds 2개 이상 검증 + improvement가 인용한 소스의 concern 낱말을
  언급하는지 코드로 재확인 → 실패하면 문서의 원래 폴백("만들지 않음")을 그대로 적용. **AI 판단만으론
  100%를 담보 못 한다.**
