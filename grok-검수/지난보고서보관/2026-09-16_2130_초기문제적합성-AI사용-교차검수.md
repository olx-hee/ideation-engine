## 0. 한 줄

해커톤·공모전 오프라인 첫 회의로 대상을 좁힌 것은 **원래 문제 쪽으로의 코스 수정**이다.  
그러나 인계서 §2의 15화면·스킬맵·막힘 감지는 **기획 확정이지 구현이 아니며**, 실제 앱은 아직 **주제 발산 목업 + 오케스트레이터/비용 미터가 더 완성된 상태**다.  
마무리 산출물(주제 + 임시 역할 + 액션 1~2 + 다음 확인)은 목적 확대가 아니라 **초기 문제의 최소 완결**이다.

**Blocker 0 / High 3 / Medium 4 / Low 1 / Question 1**

## 1. 방향 판정 — 현재 주제에 맞는가

원래 문제: *회의 진행 능력 부족 → 팀플 첫 대면 비효율.*  
현재 공표 주제: *대학생 해커톤·공모전, 오프라인 첫 회의, 계정 없이 링크/방 코드.*

| 축 | 판정 |
|----|------|
| 대상 축소(해커톤 첫 회의) | **맞음.** 일반 팀플·비동기 온라인까지 품으면 제품이 다시 흐려진다. |
| 주제 결정 코어 | **맞음.** 해커톤 첫 회의의 핵심 구간이다. |
| 오케스트레이터·벤치·비용 미터 | **보조만.** 초기 문제를 푸는 실체가 아니다. `1941`이 이미 “간판이 측정에 눌려 진화”라고 했고, 지금은 그 간판이 제품보다 앞선 상태다. |
| 15화면·자동 막힘 진단 | **과함.** 초보 팀의 첫 대면을 앱 따라가기로 바꿀 위험이 있다. |
| 마무리(역할·다음 스텝) 제외 | **과도한 축소.** 절제가 아니라 원래 문제를 반만 푸는 것이다. |

**이탈은 아니다. 다만 무게중심이 아직 퍼실리테이션이 아니라 모델 라우팅에 있다.**  
다음 슬라이스는 새 kind/diagnose API가 아니라, **실제 아이디어가 보고서·마무리까지 이어지는 한 줄**이어야 한다.

## 2. Claude 5질문에 대한 합의 답

### Q1. 초기 문제 적합성 — 주제만 푸는 게 절제인가, 반만 푸는가?

**반만 푸는 것이다.** 둘 다 동의. Claude 갭 진단은 맞다. “잘 만족한다” 쪽은 과하다.

첫 대면이 성공하려면 최소한 다음으로 끝나야 한다.

1. 무엇을 만들지 정했다.
2. 누가 첫 행동을 맡을지 정했다.
3. 언제 다시 볼지 정했다.
4. 미합의 사항이 뭔지 안다.

지금 코드는 1번도 세션 데이터로 만들지 못한다. 보고서는 고정 샘플이다 (`src/App.jsx` 53–67, 859–910).  
역할·다음 스텝을 **전부** 빼는 것은 절제가 아니다. 기대치 조율 전체·프로젝트 관리까지 넣는 것도 아니다.

### Q2. 마무리 산출물·역할 제안 — 완결인가, 목적 확대인가?

**1·2는 초기 문제의 최소 완결.** 보고서에 얹는 방식(Claude 제안)이 안전하다.

| 넣어도 됨 | 안전선 밖 |
|-----------|-----------|
| 선정 주제 | 칸반·장기 일정·반복 알림 |
| 임시 역할 **후보**(확정 아님) | 성격·헌신 예측, 기여도 평가 |
| 바로 할 일 1~2 + 담당자 | 당사자 동의 없는 자동 배정 |
| 다음 확인 시점/연락 | 프로젝트 전 과정 관리 |
| 미해결 질문 1~2 + 전원 확인 | “스킬이 있으니 이 역할” 확정 |

제안 3(아이스를 “서로 알기”로): 가볍게면 OK. 제안 4(기대치): **확대 쪽**. 가용 시간 한 줄 정도만.

### Q3. AI 사용 — 과한가 / 부족한가 / 엉뚱한가?

**혼합. 핵심 문제에 대해선 라우팅은 부차, 막힘 자동진단은 엉뚱, 검색 분리·스킬맵은 방향이 맞다.**

- **작업별 라우팅:** 구현은 있다. 활성 경로는 전부 `small` (`server/orchestrator/registry.js` 23–29). “저가/고가 자동 배분”이 아니다. 첫 대면 비효율을 직접 풀지 않는다.
- **Brave 검색:** 해커톤 주제 중복 검토에는 적합. 단 Brave가 **라벨을 판정하지 않는다.** 검색 결과를 DeepSeek이 판정한다 (`server/orchestrator/index.js` 99–114). UI 748행의 “Brave가 확인”은 과함. 792행 주석이 더 정직하다.
- **팀 스킬맵:** 첫 대면(“서로 모름”)에 가장 가까운 기능인데 **코드에 없다.** 발산 각도만 있다 (`assignTeamAngles`).
- **막힘 감지(유사도·발언분포):** 코드에 없고, 오프라인 소규모에서는 **신뢰할 수 없다.**
  - 앱은 음성을 모른다. 제출 개수 ≠ 발언량.
  - 3~5명이 같은 주제를 쓰면 유사도는 정상적으로 올라간다.
  - 좋은 합의와 집단사고를 구분하지 못한다.
  - 선행 `0145`/`1210`: 막힘은 **상시 진단이 아니라** ‘이미있음’ 뒤·호스트가 켠 온디맨드.

**권장 신호:** 경과 시간 + 아이디어 수처럼 관찰 가능한 규칙만. “막힌 것 같나요?” 팀 확인. 출발점/비틀기/돌아가며는 **도구**이지 자동 처방가 아니다. 발언 쏠림은 AI보다 “한 사람 한 줄” 규칙이 낫다.

### Q4. 대체 vs 보조 — 진행자 수락이면 충분한가?

**절차는 자동화, 사람 결정은 보조. “진행자 수락”만으로는 부족하다.**

초보 진행자에게 매 판단를 넘기면 진행 부담이 안 줄어든다. AI가 주제·역할을 확정하면 권한이 과하다.

- 타이머·라운드 순서·다음 단계 안내: 기본 진행, 건너뛰기 가능
- 막힘 도구: 근거와 함께 제안, 진행자 **또는 팀**이 켬
- 현실성 라벨: 참고 의견
- 주제·역할·담당: 팀이 직접 확인. 역할은 당사자 동의

이건 선행 human-first(`1210`)와 같다. 자동 diagnose → 매핑은 그 원칙에서 **한 걸음 후퇴**다.

### Q5. 정직성 — 과장 위험은?

있다. “시연용” 배지는 잘 붙어 있다. 그래도 위험:

1. **효과 주장.** 외부 팀 데이터 없음 → “첫 대면 비효율을 줄인다” 금지. 증명된 것은 기능 동작·모델 실험뿐.
2. **§2 “확정 상태”.** §5는 설계·목업이라고 인정하면서 §2는 15화면을 현재처럼 적었다. 읽는 사람은 구현으로 읽는다.
3. **성능 우위.** 셀프체크는 맞다. README의 대등·절감 서사는 소표본·LLM 심판 한계를 항상 같이 붙여야 한다.
4. **Brave가 판정.** 검색 근거 vs 라벨 판정을 섞지 말 것.
5. **비용 절감.** 활성 모델이 전부 small이면 flagship 대비 절감은 구조적으로 나온다. **단일 저가 모델** 기준선이 있어야 한다(기획 §1-3과 동일).
6. **Langfuse/promptfoo**는 관측 도구이지 외부 검증 기관이 아니다.

· 재현: 목표·아이디어를 바꿔도 최종 주제는 “AI 커뮤니케이션 퍼실리테이터”.

[High] 자동 막힘 감지(유사도·발언분포)를 핵심으로 두면 초기 문제를 빗나감

· 재현: 4명이 같은 해커톤 주제로 짧은 문장을 내면 유사도는 올라가고, 오프라인 발언은 앱에 안 남는다.  
· 제안: diagnose API를 개발 선행 조건에서 뺀다. MVP는 타이머 + 아이디어 수 + 진행자/팀 “도구 켜기”.

[Medium] `server/orchestrator/registry.js:23-29` — “저가/고가 자동 배분”과 코드 불일치  
· 문제: 활성 라우트 전부 small. 난이도 엔진이 아니라 작업별 정적 모델 선택.  
· 제안: 발표·인계 문구를 “작업별 모델 선택”으로. 동적 승격은 미구현.

[Medium] `src/App.jsx:747-748` vs `server/orchestrator/index.js:99-114` — Brave 판정 과잉  
· 문제: Brave는 근거, 라벨은 DeepSeek.  
· 제안: “Brave가 근거를 찾고 AI가 임시 판정”으로 통일. 792행 수준.

[Medium] 15화면은 그 자체로 첫 대면 비효율을 재생산할 수 있음  
· 문제: 60–90분 초보 팀이 화면 15개를 따라가면 대화가 아니라 앱 조작이 된다.

· 문제: 발산 AI 카드는 동적 보조가 아니라 스크립트.  
· 제안: “구조화된 진행 템플릿”으로 부르고, 실호출 연결 전까지 시연용 유지.

## 4. 두 검수자 — 합의 / 불합의

### 합의 (채택)

- 대상 축소는 타당. 방향은 유지(Conditional Go).
- 주제만으로 첫 대면을 풀었다고 하면 안 된다.
- 마무리 산출물 = 목적 확대 아님. 최소 완결.
- 막힘 자동진단(유사도·발언분포)은 오프라인에서 약하다. 규칙 + 사람 확인.
- AI는 절차를 밀고, 사람 관련 결정은 팀이 확인.
- 실사용 데이터 전 효과 주장 금지.
- 인계 §2와 코드 간극을 먼저 고치는 문서 정직성이 필요.

### 불합의 (정리자 채택 = Grok)

| 쟁점 | GPT Sol | Grok | 이번 보고서 |
|------|---------|------|-------------|
| 다음 1순위 | 다중 입장 + B1 | 실제 아이디어→보고서 배선, 그다음 마무리 | **배선 → 마무리 → 단순 막힘 도구.** B1은 **링크 실공유 전 필수**이나, 로컬 퍼실리테이션 완성의 1순위는 아님 |
| §2 High의 성격 | 구현이 없다 | §5가 이미 설계·목업을 인정. 문제는 라벨(“확정 상태”) | High 유지. 사유는 **독자가 구현으로 읽게 만든 표기** |
| “정면 해결” 부정 강도 | 현재 흐름이 정면 해결한다는 평가에 비동의 | 코스 수정 자체는 긍정, 만족도 문장만 과함 | 방향은 긍정, 만족 주장은 불채택 |

Claude 자체 갭(절반만 충족, 스킬맵 미연결, 효과 데이터 없음)은 **둘 다 채택**. “단계·타이머·막힘뚫기로 정면 대응”은 **불채택**(막힘뚫기는 미구현).

| 3 비용 기준선 | **단일 저가 모델 1개**를 반드시 고른다. flagship 가상 비교는 보조 숫자. |
| 4 뚫기 3종 | 도구로만. 기본 경로는 자유 입력 + “한 사람 한 줄”. 비틀기 질문은 2~3개, 돌아가며는 원라운드. |
| 5 프로필·스킬맵 | 대기실 다음 한 화면. 강점/약점 태그는 도메인당 소수. 각도·현실성(“우리 팀으로 만들 수 있나”)·마무리 역할 후보에 연결. |
| 6 마무리 | **넣는다. 목적 확대 아님.** 보고서 하단에 주제 + 역할 후보 + 액션 1~2 + 다음 확인 + 전원 확인. 기대치 전체는 넣지 않음. |

### 권장 구현 순서

1. 실제 아이디어(및 투표) → 분석/보고서 텍스트 연결. 시연용 고정 본문 제거 또는 폴백 명시.
2. 세션 끝 마무리 블록 + 전원 확인.
3. 스킬 공백 한눈 보기 → 역할 **후보**.
4. 단순 규칙 막힘 도구(버튼). 자동 매핑 없음.
5. 외부 학생 팀 3~5회 관찰. **그 전에 효과 문구 금지.**
6. 오케스트레이터·비용 최적화는 위가 돈 뒤에만.
7. 초대 링크/방 코드를 실제로 나눠 주기 **직전** B1 + 세션별 AI 쿼터.

## 6. 보안

이번 범위는 방향 문서이나, 인계가 링크/방 코드 제품을 “확정”으로 적었으므로 보안면은 해당 있음.

- **인가 없음:** 세션 UUID를 알면 phase·ideas·votes 변경 가능 (`server/index.js` 99–174). UUID는 추측 방지이지 인가가 아니다.
- **`POST /api/ai`:** 유효 세션 없이도 호출 가능 (178–192). IP당 분당 60회만. 유료 키 연결 시 과금 남용 High.
- **B1 제외 결정:** 같은 방·로컬 시연에는 임시 허용. **실링크 공유·실 AI 배포의 선행 조건**이지 “오프라인이니까 영구 제외”가 아니다.
- **다공급사 전송:** 팀 아이디어가 OpenRouter 등으로 나간다. 첫 회의 실사용 전에 제3자 전송 고지 필요.
- **프로덕션 인메모리 폴백:** 기존 하드닝 잔여. 이번 diff에서 새로 열리지는 않음.

**보안 한 줄:** 로컬 퍼실리테이션 완성까지는 capability URL로 버틸 수 있으나, 방 코드를 제품 전면에 두는 순간 B1·AI 쿼터 없이 배포하면 안 된다.

## 7. 채팅용 요약

- **판정:** Conditional Go. 해커톤 첫 대면으로 좁힌 방향은 맞다.
- **채택:** 마무리 산출물 + 스킬맵→역할 **후보**. 목적 확대 아님.
- **불채택:** 유사도·발언분포 자동 막힘 진단, 15화면을 현재 구현처럼 적기, 효과 주장, Brave가 판정한다는 말, 저가/고가 자동 배분.
- **다음:** 가짜 보고서부터 실제 세션에 붙이고, 그 하단에 마무리를 얹는다.
