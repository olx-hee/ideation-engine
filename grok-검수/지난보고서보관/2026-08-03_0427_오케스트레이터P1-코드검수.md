## 0. 요약 판정

P1 목표(목업 + 정적 라우팅 + 비용 미터 + 발표 화면)는 **대체로 설계 §9를 지켰다.**  
분류기·캐스케이드·실호출·repair/verify 엔진은 없고, `planStub`은 고정 목업이다.  
미터 공식도 **generate만 절감 분모·가상 allFlagship·estimate-mock**으로 §5 핵심을 코드에 박아 두었다.

다만 (1) **무인증 `sessionId` → `meters` Map 오염/성장**, (2) **GET `/ai-meter`가 빈 미터를 생성**하고 레이트리밋이 없음, (3) 발표 패널에 **escalateRate·overhead 미표시** 및 **report 콜과 미터 fetch 레이스**, (4) React StrictMode에서 **kind당 이중 호출** 가능 — 이 네 가지는 발표·P2 전에 손볼 가치가 있다.

**Blocker 0 / High 1 / Medium 5 / Low 4 / Question 1**

## 2. [2] 비용 미터 정직성 (§5)

### 2-1. 규약 대조

| §5 / 요청 항목 | 코드 | UI | 판정 |
|----------------|------|-----|------|
| purpose 분리, **generate만** 절감 분자·분모 | `gen = purpose==="generate"`; `ourCost`/`allFlagshipCost`는 gen만 | 절감%는 이 값 사용 | ✅ |
| overhead 분리 집계 | `overheadCost` 계산됨 | **화면 미표시** | ⚠️ 코드 OK / UI 공백 |
| allFlagship = 가상 비교 | 주석 + 재계산식; `baselineNote` 문구 | `※ {baselineNote}` 렌더 | ✅ |
| `pricingMode=estimate-mock` → 추정 배지 | `PRICING_MODE` 상수 | `measured`가 아니면 「추정(목업 단가)」 | ✅ |
| escalateRate 자리 | summary에 숫자 계산 | **미렌더** | ⚠️ 자리만 서버 |
| 목업 단가 | `TIER_PRICE` + `estCost` | 배지로 출처 암시 | ✅ |

### 2-2. 절감% 계산식

```
savedPct = round( (1 - ourCost / allFlagshipCost) * 100 )
ourCost         = Σ estCost(실제 tier, tokens)  for purpose=generate
allFlagshipCost = Σ estCost("flagship", tokens) for purpose=generate
```

- **오버헤드를 분모·분자에 넣지 않음** → 이중집계·숨은 과금 함정은 **현재 generate-only 경로에서 없음**.
- 전 콜이 이미 flagship이면 0% — 정상.
- idea fan-out(전부 small) + analyze/report(flagship) 조합이면 절감%가 크게 나와 **데모에 유리**하고, 공식 자체는 가상 베이스라인으로 정직하다.

### 2-3. 함정·과장 포인트

| 이슈 | 심각도 | 설명 |
|------|--------|------|
| escalateRate·overheadCost UI 누락 | **Medium** | §5 「절감%만 크게 두지 말고 승격률·품질 지표 병기」. P1에 승격은 0이어도 **「승격률 0%」·「오버헤드 $0」**을 작게 보여 주는 편이 발표 Q&A에 안전 |
| usage 난수 | **Low~Medium** | `adapter` `outTok = 120 + random*300` → 같은 세션 재현 시 절감%·$가 흔들림. 데모 재현성(§8)과 충돌. P1은 시드로 고정하거나 kind별 고정 usage 권고 |
| in/out 미분리 | **Low** | 설계는 `usageTokensIn/Out`. 합산만 있음 — P2 usage 필드 대비 자리 부족 |
| 캐시 절감 라인 | **Low** | P1 불필요. P2 체크리스트용 주석/필드 `cacheSavedCost: 0` 자리만 있어도 됨 |
| 「약 N% 절감」시각 강조 | **Low** | 배지·각주가 있어 과장 **차단은 됨**. 다만 초록 대형 숫자가 먼저 보이므로 배지를 더 눈에 띄게 해도 좋음 |

**미터 핵심 공식: 합격.** UI가 §5 체크리스트를 아직 다 보여 주지는 않음.

## 3. [3] 보안·견고성

### 3-1. `meters` Map · sessionId · 무인증 — **High**

```js
// orchestrator/index.js
function meterFor(sessionId) {
  if (!sessionId) return makeMeter();
  if (!meters.has(sessionId)) meters.set(sessionId, makeMeter());
  return meters.get(sessionId);
}
```

| 벡터 | 위험 |
|------|------|
| `POST /api/ai` + 임의 `sessionId` | B1 없이 **남의 세션 미터 오염** 또는 **새 키 무한 생성**. 콜마다 `calls[]` 증가 |
| `GET /api/sessions/:id/ai-meter` | **레이트리밋 없음**. `sessionMeter` → `meterFor`가 **조회만으로 Map 엔트리 생성** → UUID를 찍으면 메모리 증가 |
| 세션 존재 검증 없음 | `store.get(id)` 없이 미터 네임스페이스가 열림 |
| TTL/상한 없음 | 프로세스 살아있는 동안 Map 성장 |
| aiLimiter 20→**60**/min | 목업에선 금전 피해 없음. **P2 실키 순간** 비용·오염 가속 |

**High:** 무인증 + 조회 시 생성 + 무제한 Map은 P1 데모에서도 DoS·발표 수치 조작에 열린다.  
**최소 가드(구현 권고, 이번 검수는 수정 안 함):**
1. `meterFor`/`sessionMeter`: **기존 키만 조회**, 없으면 `{ calls: [], … }` 생성 없이 반환  
2. `POST /api/ai`: `sessionId` 있으면 `store.get`로 존재 확인, 없거나 불일치 시 일회성 미터 또는 404  
3. Map: **max entries**(예: 200) + LRU/TTL(예: 2h)  
4. `GET .../ai-meter`에도 rate limit  
5. P2 전 aiLimiter를 다시 보수적으로(또는 일일 쿼터) + B1

### 3-2. kind 화이트리스트 · 입력 크기

| 항목 | 판정 |
|------|------|
| `ORCHESTRATOR_KINDS.includes(b.kind)` | ✅ 유지 |
| `kind` 생략 시 `"idea"` | OK (의도에 맞음) |
| `goal` 500 / `context` 2000 / `sessionId` 64 | ✅ 유지·추가 |
| `/api/ai/plan` request 500 | ✅ |

### 3-3. 프롬프트 인젝션

- 현재: `prompt`는 **목업 usage 길이**에만 쓰임 → **지금 무해**.
- P2: goal/context를 모델에 넣을 때 §8대로 **delimiter + 읽기 전용 블록**, 시스템 지시와 분리 필요.
- **Medium(자리 박기):** `adapter.js`에 `buildPrompt({ system, userGoal, context })` 스켈레톤과 TODO 주석을 P2 전에 두는 것을 권고.

### 3-4. 기타

| 항목 | 심각도 | 내용 |
|------|--------|------|
| React StrictMode 이중 effect | **Medium** | `main.jsx` StrictMode + `aiFired` useRef는 remount 시 리셋 → **dev에서 kind당 2회** 누적 가능 → 발표 수치가 부풀거나 불안정. 서버 멱등 키(`sessionId+kind`) 또는 ref 대신 module/sessionStorage 가드 |
| 오케스트레이터 응답 미사용 | **Low** | UI는 기존 시연 템플릿 유지, AI는 미터 전용 — 정직(시연용 배지와 일치). 단 심사자가 「AI 분업 텍스트는 어디?」 물으면 “미터·라벨만 P1”이라고 답할 것 |
| `keyword` kind | **Low** | 레지스트리에 있으나 프론트 step 매핑에 없음 — 죽은 라우트에 가깝음 |

## 4. [4] ReportPhase 발표 패널 정직성

### 실제로 렌더되는 것

| 요소 | 렌더 여부 | 비고 |

| 「추정(목업 단가)」배지 | ✅ | `pricingMode !== "measured"` |
| 모델·역할·티어(저가/중가/고가) 목록 | ✅ | `calls` 전체 |
| `savedPct` / `ourCost` / `allFlagshipCost` | ✅ | |
| `baselineNote` (가상 비교) | ✅ | `※ …` |
| escalateRate | ❌ | |
| overheadCost | ❌ | |
| purpose 라벨 | ❌ | 전부 generate라 지금은 OK |

### 과장 여부

- **의도적 과장으로 보기는 어렵다** — 추정 배지 + 가상 비교 주석이 같이 있다.
- 남는 리스크:
  1. **레이스 (Medium):** step=3에서 `api.ai('report')`와 `getAiMeter`가 동시에 나가 report 콜이 빠질 수 있음 → 패널이 불완전하거나, 재진입 시에만 완전. `ai` await 후 meter fetch, 또는 meter를 ai 응답에 실어 ReportPhase로 전달.
  2. **calls에 purpose 미구분 표시 (Low):** P2에서 route/repair가 섞이면 분업 목록이 절감 공식과 어긋져 보일 수 있음 → generate만 나열하거나 purpose 뱃지.
  3. 보고서 본문은 여전히 「시연용 고정 템플릿」— 패널과 분리되어 **정직**.

## 5. [5] 놓친 것 · P2 전에 자리 박을 것

우선순위 순.

1. **meters 가드** — 조회 시 생성 금지, 세션 존재 확인, TTL/상한, GET 레이트리밋 (High 완화)  
2. **kind 멱등** — 서버 `recordedKinds: Set` per session 또는 client+server 이중 가드 (StrictMode·재전송)  
3. **패널 지표** — `escalateRate`, `overheadCost` 작은 텍스트; P2용 `schemaFailRate: null` 자리  
4. **adapter 프롬프트 빌더 + delimiter TODO** — 실연동 시 인젝션 1차 방어  
5. **capability 플래그 빈 자리** — registry model 엔트리에 `{ supportsJsonSchema: false, … }`  
6. **usage in/out 분리·시드 고정** — 데모 재현성 + P2 measured 전환  
7. **aiLimiter 정책** — 실키 전 한도·쿼터 문서화; 60/min이 의도인지 재확인  
8. **죽은 `ai.js` 정리** · health의 `mock-pending`과 orchestrator mock 메시지 정합  
9. **골든 세션 픽스처(§7)** — P2 튜닝 전에 고정 goal·기대 티어 표 1세트라도  
10. **캐시 절감 필드 0** — §5 체크리스트 자리만
