## 0. 한 줄 결론

**멀티 LLM은 “모델 개수”가 아니라 “역할 분업 + 티어 라우팅 + (선택) 교차 검증”일 때** 단일 AI+긴 프롬프트 대비 품질·비용·제품 설명력에서 이점이 난다.  
맹목적 병렬 투표·전부 flagship은 오히려 비용·지연·톤 불일치를 키운다.

**권장:** 4~6개 모델 축 + `kind → model` 라우팅. 호출의 대부분을 저가/저지연 워커에, flagship은 보고서·오케스트레이션·깊은 비판 등 소수 지점에만.

---

## 1. 왜 이 논의가 필요한가

IdeationEngine의 핵심 가치는 결국 **세션을 진행하며 AI가 개입하는 지점**(자극, 각도, 테마, 보고서)이다.

초기 피드백의 요지:

> 단일 모델에 프롬프트만 잘 써서 돌리는 제품과 무엇이 다른가?

답으로 쓸 수 있는 구조적 차별:

| 단일 AI + 프롬프트 | 잘 짠 오케스트레이션 |
|--------------------|----------------------|
| 한 모델이 발산·비판·정리를 모두 흉내 | 단계·역할마다 **다른 전문성** |
| 낙관/환각을 스스로 검증하기 어려움 | 다른 모델이 **반박·필터** |
| 전부 같은 단가 | 쉬운 일은 싸게, 어려운 일만 비싸게 |
| “AI 챗봇”으로 설명됨 | “세션 구조에 박힌 AI 분업”으로 설명됨 |

마케팅 문구는 **「멀티 LLM」보다**  
**「단계·역할에 맞춰 AI가 분업하고, 결과가 투표·보고서까지 이어진다」** 가 맞다.

## 2. 섞으면 정말 이점이 있나? (다축 분석)

### 2.1 품질

**이점 (분업·검증일 때)**
- 발산 / 비판 / 정리를 다른 모델·시스템 프롬프트에 고정 → 단계별 안정성
- A 결과물을 B가 검증 → 과한 낙관·환각 감소 (Six Hats·분석과 궁합)
- 모델 톤 차이로 발산 다양성↑, 한국어 축(Qwen/DeepSeek 등)으로 UI 톤 개선 여지

**역효과**
- 라우팅이 허술하면 잘못된 모델에 잘못된 일 → 단일 우량 모델만 못함
- 모델마다 말투·스키마가 달라 세션 톤이 들쭉날쭉
- “여러 모델 답을 나열/투표만” 하면 비용↑ 품질 향상은 미미한 경우 많음

**결론:** 품질 이점은 **개수가 아니라 파이프라인 설계**에 있다.

### 2.2 토큰·비용

**이점 (티어 라우팅일 때)**
- 호출의 70~90%를 Flash/Haiku/mini/DeepSeek/Nemotron Nano 등으로
- flagship은 세션당 소수
- 실무에서 흔히 거론되는 **총비용 40~80% 절감**은 이 패턴의 경험 구간 (자세한 설명 → §5)

**역효과**
- 동일 입력을 모델 N개에 병렬 → 토큰 ≈ N배
- 오케스트레이터가 매 턴 flagship으로 “누구 쓸지”만 고민 → 절감 잠식
- reasoning 모델의 thinking 토큰을 짧은 힌트에 상시 사용 → 비용 폭탄
- 한국어는 토크나이저 효율이 영어보다 나쁜 편 → 무분별한 멀티콜에 더 민감

### 2.3 지연·UX

| 방식 | 체감 |
|------|------|
| 단일 중형 | 예측 가능 |
| 싼 워커 라우팅 | AI 카드·키워드가 더 빨라질 수 있음 |
| 다모델 병렬 경합 | 가장 느린 쪽에 맞춤 → 불리 |
| 직렬 파이프라인 | 대기 증가, 대신 “진행감” 연출 가능 |

실시간 세션 제품 → **병렬 3모델 경합보다 단계별 1모델 + 가끔 교차검증 1회**가 맞다.

### 2.4 안정성·운영

**이점:** 공급사 페일오버, 가드레일 모델 분리(NemoGuard 등)  
**비용:** 키·쿼터·스키마·프롬프트 버전·파싱 실패를 모델 수만큼 관리. 평가 체계 없으면 개선이 감에 의존.

### 2.5 제품 차별화 (피드백 대응)

| 주장 | 단일 AI | 잘 짠 멀티 |
|------|---------|------------|
| AI가 아이디어를 도와준다 | 충분 | 차별 약함 |
| 단계·역할마다 다른 전문 AI | 프롬프트 흉내 | **데모·설명 가능** |
| 한 AI 낙관을 다른 AI가 검증 | 어려움 | **구조적 장점** |
| 세션당 비용 통제 | flagship만 쓰면 비쌈 | 라우팅 시 **유리** |

## 5. 「총비용 40~80% 절감」상세

### 5.1 이 수치가 의미하는 것

- **Before:** 거의 모든 요청을 flagship/중상 모델 하나  
- **After:** Small ~70% / Workhorse ~25% / Flagship ~5% 같은 **티어 라우팅**  
- 결과: 월 API 청구액이 Before 대비 대략 **40~80% 감소**했다는 **업계 경험 구간**  
- 성격: 벤더·플랫폼·에이전트 가이드에서 반복되는 운영 패턴 설명. **만능 보장 수치가 아님.**

핵심 식:

> 절감 ≈ (비싼 모델로 보내던 호출 중 ‘싸도 되는’ 비율) × (단가 차이)

### 5.2 왜 그 정도인가

1. 토큰 단가가 티어 간 **수십 배** 차이  
2. 실제 트래픽은 **쉬운 요청이 대부분**(긴꼬리)  
3. 출력·reasoning(thinking) 토큰이 비싼데, 짧은 자극에는 그걸 쓸 필요가 없음  

### 5.3 설명용 단순 계산 예

- 월 100만 요청, 요청당 비용 Before $0.01 → **$10,000**  
- After: 70%×$0.001 + 25%×$0.008 + 5%×$0.03 ≈ **$4,200**  
- ≈ **58% 절감**  
싸구려 비중·단가 차가 크면 80%에, 어려운 요청이 많으면 40% 아래로.

### 5.4 실무에서 쓰는 방식

| 패턴 | 내용 |
|------|------|
| 규칙 라우터 | `kind`/작업유형/플랜별로 model 고정 (MVP에 최적) |
| 난이도 분류기 | 작은 모델로 난이도 판정 후 티어 선택 |
| 캐스케이드 | 싼 모델 초안 → 불합격만 비싼 모델 재시도 |
| 페일오버 | 장애 시 다른 공급사 (비용 2순위) |
| 캐시·배치 | prompt caching, Batch API로 추가 절감 |
| 관측 | Langfuse 등으로 model별 $/토큰/에러 모니터링 후 주간 조정 |

### 5.5 절감이 안 나오거나 과장되는 경우

- Before가 이미 mini/Flash  
- 매 요청 3모델 병렬 투표  
- 오케스트레이터를 매 턴 Opus로 돌림  
- reasoning을 짧은 힌트에 상시 사용  
- 파싱 실패 재시도로 중복 과금  
- 긴 세션 로그를 매 호출에 통째로 첨부  

### 5.6 IdeationEngine 티어 배정 (초안)

| 호출 | 티어 | 이유 |
|------|------|------|
| 아이스/아이디어 직후 AI 카드 | Small | 빈도 높음 |
| 방식 추천·각도 힌트 | Small | 짧음 |
| SCAMPER/Six Hats 질문 | Small~Mid | 중간 |
| 테마 클러스터링 | Mid | 품질 민감 |
| 검은 모자·리스크 | Mid + 가끔 Reasoning | 제한적 |
| 최종 보고서 | Mid/Flagship | 세션당 1~2회 |
| 오케스트레이터 | Mid 위주 | 매 턴 flagship 비권장 |

## 6. 설계 원칙 (실행 체크리스트)

1. **모델은 4~6개 축**으로 시작 (10개 동시 연동 금지)  
2. **`kind` → tier/model`** 테이블을 서버에 두기 (키는 서버만)  
3. 호출의 **대부분 = Small**, flagship = 세션당 소수  
4. 교차 검증은 **매 턴이 아니라** 분석·보고서·검은 모자 등 선택 지점  
5. 병렬 “다모델 경합”은 기본 금지 (지연·토큰)  
6. reasoning은 **비판/난이도 높은 판단**에만  
7. 출력은 JSON 스키마로 통일해 모델 교체 비용 낮추기  
8. 상용화 시 가드레일 모델 분리 + 기존 검수의 AI 쿼터·인증(B1)과 결합  
9. 라우팅 효과는 **$/세션·$/kind 대시보드**로 증명 (감이 아니라 수치)  
10. 제품 카피는 “멀티 LLM”이 아니라 **분업·검증·세션 연결**
