# 왜 이렇게 만들었나 — 설계 결정 기록 (팀원용)

> "무엇을 만들었나"가 아니라 **"어떤 고민을 했고, 어떻게 확인했고, 왜 이 결론을 냈나"**를 남긴 문서입니다.
> 커밋 로그만 봐선 "왜"가 안 보여서, 팀원이 맥락을 알 수 있게 정리했습니다.
> (실험 원자료는 [`benchmarks/`](../benchmarks) · [`eval/`](../eval), 정직성 교차검수는 [`grok-검수/`](../grok-검수)에 있습니다.)

우리 개발은 한 가지 원칙 위에서 굴러갑니다: **주장하기 전에 측정하고, 측정을 외부 도구·다른 AI로 교차검증하고, 틀린 가설은 정직하게 버린다.**

---

## 결정 1 — "여러 AI를 자동으로 섞으면 더 좋다"를 **버렸다**

**처음 생각:** 여러 LLM을 자동으로 섞어(앙상블) 하나로 합치면 단일 모델보다 더 창의적이고 좋을 것이다. (이게 초기 차별점이었음)

**어떻게 확인:** 같은 작업을 단일 vs 다중으로 여러 번 블라인드 대결시키고, 다양성 지표(Vendi)·비용까지 쟀다. (`benchmarks/rematch.json`, `confound.json`, `diversity-remeasure.json` 등)

**결과:** 반증됐다. 서로 다른 모델을 자동으로 섞으면 **오히려 뻔해지고(다양성↓) 비쌌다.** 단일 강모델이 더 다양하고 쌌다. "약한 모델을 섞으면 품질이 희석된다"는 현상.

**그래서:** *"자동으로 섞어 더 창의적"*이라는 간판 한 문장을 버렸다. (교란을 제거하니 착시였음)

---

## 결정 2 — 대신 **작업마다 측정으로 고른 모델**(role map)

**고민:** 그럼 여러 AI를 어떻게 정직하게 쓰나?

**확인:** 작업(키워드·발산·분석·보고·검증)마다 여러 모델을 블라인드로 대결시켜 1등을 뽑았다. (`benchmarks/heavy-analyze.json`, `report-retest.json`, `verify-bench.json`)

**결론(role map):** 키워드=Flash-Lite / 발산·분석=Solar / 보고=DeepSeek / 검증=Llama(만든 모델과 다른 것). **작업마다 1등이 달랐다.**

**왜 이게 정직한 다중인가:** "많이 쓰니 좋다"가 아니라 **"일마다 측정으로 이긴 모델 하나"**를 쓰는 것. 자동 섞기(반증됨)와 다르다.

## 결정 3 — 비용·품질을 **외부 오픈소스 도구로 검증** (우리끼리 계산 아님)

**고민:** "저렴하지만 좋다"를 우리가 스스로 계산하면 *"유리하게 잰 거 아냐?"* 소리가 나온다.

**확인:**
- **비용 = [Langfuse](https://github.com/langfuse/langfuse)**(오픈소스 관측). 우리 모델 vs 최고급 Claude-Opus를 **둘 다 실제로 돌려** 실비용 비교 → **약 99.8% 저렴**(가정 아님). Langfuse가 같은 값을 독립 기록. (`langfuse-verify-full.mjs`)
- **품질 = [promptfoo](https://github.com/promptfoo/promptfoo)**(오픈소스 평가). 우리 모델 vs Opus를 **제3의 심판 AI**가 채점 → **동급**(분석 0.95 vs 0.90 등). (`eval/`)

**왜:** 외부 도구의 기록이 있으면 "우리끼리 계산"이 아니게 된다. (정직성 = 우리 핵심 원칙)

**정직한 한계:** 점수가 천장에 몰려 "명확히 낫다"가 아니라 **"동급"**. 심판도 결국 AI라 객관 작업엔 믿을 만하지만 창의 판정은 사람이 필요.

## 결정 4 — 창의 사람축을 재보니, 진짜 문제는 "다중이냐"가 아니라 **"현실성"**이었다

**고민:** LLM 심판은 창의성 판정에 편향(다듬어진 것 선호)이 있다. 사람은 다르게 볼까?

**확인:** 단일 vs 다중 발산 아이디어를 **사람이 블라인드로 좌/우 택1**. (점수 없이 직감)

**결과:** **단일 4 : 다중 2** — 사람 눈에도 다중이 우위가 아니었다(노이즈). 그런데 더 중요한 발견: 나온 아이디어들이 **VR 가상 식탁·블록체인 팀기여도 같은 공상**이라 애매했다.

**원인:** 발산 프롬프트가 `[참신함]` + "현존 안 하는 것"만 요구 → **실현가능성·수요·"왜 아직 없나"를 안 봄** → 공상 유도.

**그래서 진짜 레버 발견:** "단일이냐 다중이냐"가 아니라 **"아이디어가 현실에 발 붙는가"**. → 다음 결정으로.

## 결정 5 — **현실성 게이트 + 시중검색(Brave)** 추가

**무엇을:**
- **현실성 패스**(`reality`): 아이디어마다 실현가능성 / 왜 아직 없나 / 넘는 법 / 진짜 수요를 붙임. (공상·뻔함 둘 다 배제)
- **시중검색 게이트**(`market`): **"이거 이미 있나?"를 AI가 아니라 실제 검색(Brave)**이 확인 → 이미있음/유사/공백 판정 + 진짜 URL.

**왜 검색을 따로 쓰나:** "이미 있나"는 LLM이 지어낼 수 있다(환각). **검색엔진이 검색을 잘한다.** 실제로 "AI 안부전화" 아이디어에 검색이 SKT·CLOVA·CallMate를 잡아냈다 — LLM 주장이 아니라 실측.

**연결:** 이게 우리 "적재적소 분업"의 확장 — 검색은 검색도구가, 추론은 추론모델이. (자세히는 루트 README 🔬 섹션)

## 결정 6 — 개인 특성은 **"실행"이 아니라 "주제 결정"**에, 그리고 **사람이 먼저**

**첫 시도(틀림):** 프로필/강점으로 "주제 확정 후 각자 실행 스텝 배분"을 만들었다.

**정정 1:** 우리 제품은 **주제를 정하는 회의**를 돕는 것이지, 실행 배분이 아니다. → 개인 특성을 **주제·방향 결정**에 쓰는 걸로 바꿈.

**정정 2 (더 중요):** AI가 바로 주제를 뱉으면 안 된다. **사람이 먼저 회의·시드를 내고, AI는 그걸 보조**해야 한다.

**확정 설계 — AI는 기본이 아니라 fallback 보조:**
1. 팀원 **전원이 시드(관찰·불편)를 먼저** 낸다. (안 내면 AI 안 움직임 = "AI가 다 한 거 아냐?" 방어)
2. 기본 경로: 팀이 **사람 의견을 고르면** → AI는 **검증만** (시중검색 "이미 있나" + 현실성 "수정할 점"). **원문 의견은 안 바꿈.**
3. Fallback: 사람에게서 괜찮은 의견이 **안 나올 때만** → AI가 시드를 묶어 후보 3개. (근거 시드 원문 인용)

**왜:** AI가 주제를 만들거나 사람 의견을 심판하지 않는다. **결정은 사람, AI는 검색·검증·(막히면)묶기.** = 우리 정체성의 완성형.

*(상태: 이 부분은 설계·검수 완료, 프론트 배선은 진행 예정. 발산 단계의 "병렬 후보 + 이견 보존"은 별도로 남아있음.)*

## 관통하는 정체성 — "AI를 각자 잘하는 일에" (많이 쓰기 아님)

한 세션에 여러 모델·도구가 각자 역할로 참여한다: 키워드=Flash-Lite, 발산·분석=Solar, 보고=DeepSeek, 검증=Llama, **검색=Brave**, (막히면)묶기=Solar. 

- ❌ "여러 AI라서 더 창의적" (반증됨, 주장 안 함)
- ✅ **"일마다 측정으로 고른 하나 + 사람이 결정"**

## 왜 Grok과 나눠서 검수하나

주 개발은 Claude가, **방향·정직성 검수는 Cursor의 Grok**이 맡는다. 한 AI가 만들면 사각지대(자기 과장)가 생긴다. 실제로 Grok이 여러 번 우리 과장을 잡았다(예: "다중이 더 다양"이 틀렸음, "이중 독립검증" 과장 등). 검수 이력은 [`grok-검수/`](../grok-검수)에 날짜별로 남아있다.
