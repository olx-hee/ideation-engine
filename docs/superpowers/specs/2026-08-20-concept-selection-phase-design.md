# 설계 — 컨셉 선택 단계 (자동 종합 → 후보 제시 + 팀 선택)

| 항목 | 내용 |
|------|------|
| 작성 | 2026-08-20 |
| 상태 | 설계 승인됨 (사용자 확인) → 구현 계획 대기 |
| 대상 파일 | `server/orchestrator/{registry,index,adapter}.js` · `server/index.js` · `src/api.js` · `src/App.jsx` |
| 근거 | 재측정 결론(AI 기준 ≠ 사람 기준) · 2023 방향재정의 · concept-engine-test.json(엔진 결정) |

## 1. 목적

현재 앱의 종합 단계는 **AI가 팀 아이디어를 하나로 자동 결합해 테마를 정해준다**(`App.jsx`의 하드코딩 `THEMES`, "AI가 4개 아이디어의 공통 구조에서 도출"). 그러나 엄밀 재측정에서 **자동 합치기는 다양성·창의를 오히려 떨어뜨렸고**, 사람은 "다듬어진 하나"보다 **다양한 후보 중 고르기**를 선호했다(B축 4:2).

→ 종합 단계를 **"AI는 여러 갈래 컨셉 후보만 제시, 팀이 투표로 최종 선택, 안 고른 후보는 이견으로 보존"**으로 교체한다. AI가 정해주는 것 → 사람이 고르는 것.

**비목표(이번 슬라이스 제외):** 다회 토론, 검색/조사 롤(C축), 세션 간 학습, 피치의 자동 풀 리포트화. 별도 슬라이스.

## 2. 흐름

```
발산 phase (사람+AI 아이디어 풀 수집; 기존)
   ↓  pool = ideas[] 텍스트 배열
[컨셉 phase]  서버가 4개 컨셉 후보 생성 (렌즈×모델, 자동 합치기 없음)
   ↓  각 후보 = { lens, title, summary, sourceIdeaRefs[], model }
카드 뷰로 나란히 표시 → 팀 투표(online) / 사용자 선택(offline)
   ↓
최종 = 최다득표 → 피치 한 장으로 확장
   + "다른 길" 섹션 = 안 뽑힌 후보 보존(삭제 없음)
```

## 3. 생성 엔진 (다중 4모델 × 4렌즈)

- **렌즈 4개(고정):** ①실용·저비용·빠른실행 ②참신·시장차별화 ③기술 실현가능성·확장성 ④이질적 결합(의외성).
- **모델 4개:** `Solar-Pro4` · `Gemini-2.5-Flash` · `Kimi-K2.5` · `Mistral-Medium-3`. 렌즈 i ↔ 모델 i.
- 각 컨셉 = 1콜: `concept` 시스템 프롬프트 + 해당 렌즈 + [아이디어 풀] → "컨셉명 — 요약(2문장 이내)". 풀의 아이디어 2~3개를 근거로. **다른 렌즈와 겹치지 않게.**
- **합치지 않는다.** 4개를 배열로 그대로 반환.
- **엔진 결정 근거(concept-engine-test.json, n=6):** 다중(4모델) Vendi 2.794 vs 단일(Solar×4렌즈) 2.677 → 6골 중 5골 다중이 더 다양(+0.12). 비용 85배지만 세션당 1회 4개뿐이라 절대액 **$0.0085/세션 = 무의미**. "다중LLM"의 정직한 자리 = 드문 종합 단계.
- **라벨은 렌즈**로 노출(모델 브랜드 아님). model은 데이터에만 기록(투명성). "여러 AI라 더 좋다"는 클레임 없음.
- **폴백:** `OPENROUTER_API_KEY` 없거나 실패 시 렌즈별 목업 컨셉 반환(기존 adapter 폴백 패턴 준수).

## 4. 데이터 모델

```
// 세션 content에 추가 (기존 votes 메커니즘 재사용)
concept = {
  id: string,              // "c1".."c4"
  lens: "practical" | "novel" | "technical" | "cross",
  lensLabel: "실용·저비용" | ...,
  title: string,
  summary: string,
  sourceIdeaRefs: number[],// 풀 인덱스(근거 칩)
  model: string,           // 기록용(UI 비노출)
}
concepts: concept[]        // 세션당 1회 생성, 전부 보존
conceptVotes: { [conceptId]: number }   // 기존 theme votes와 동형
// 최종 = conceptVotes 최다. 나머지는 concepts[]에 그대로 → "다른 길"
```

## 5. UI (카드 뷰; `AnalyzePhase` → `ConceptPhase`)

- 상단: 주제 + 단계 표시("2 컨셉 종합") + 정직 안내(렌즈 라벨·후보만·팀 투표·이견 보존).
- **컨셉 카드 4개(2×2 그리드):** [렌즈 배지] 컨셉명 · 요약 · 근거 아이디어 칩(#n) · 투표 버튼+표수. 최다득표 카드 강조("현재 1위").
- **"다른 길" 섹션:** 안 뽑힌 후보를 이견으로 보존 표시.
- **최종 피치 카드:** 최다득표 컨셉 → 컨셉명·한 줄 피치·(누가·왜/차별점/근거) 템플릿. report phase로 연결.
- 카드 뷰 채택(비교 뷰는 이번 범위 제외).
- 스타일: 앱 기존(흰 카드·뉴트럴·에메랄드) 준수.

## 6. 코드 접점

| 파일 | 변경 |
|------|------|
| `registry.js` | `CONCEPT_LENSES`(4) + `CONCEPT_MODELS`(4) export 추가 |
| `adapter.js` | `SYSTEM_BY_KIND.concept` 프롬프트 + `MAX_TOKENS_BY_KIND.concept=300` |
| `index.js` | `orchestrate`에 `kind==="concepts"` 분기 — 렌즈×모델 fanout → **배열 반환**(synth 없음), 모델별 미터 기록 |
| `server/index.js` | 컨셉 생성 경로 — 요청에 `pool`(아이디어 텍스트 배열) 수신, concepts 배열 반환 |
| `src/api.js` | `concepts(sessionId, goal, pool)` 추가 |
| `src/App.jsx` | `AnalyzePhase` → `ConceptPhase` 개조: 하드코딩 `THEMES` 제거, 서버 concepts fetch, 카드+투표+이견+피치 렌더 |

## 7. 테스트

- **오케스트레이터:** 목업 폴백으로 `kind:"concepts"` 4개 배열 반환·형태 검증(키 없이). 실호출 시 렌즈별 실제 컨셉.
- **프론트:** 컨셉 fetch → 카드 렌더, 투표 증가, 최다득표 강조, "다른 길" 보존, 피치 카드 표시. 목업 데이터로 흐름 확인.
- **정직성:** 카드 라벨이 렌즈(모델 아님)인지, 합치기 없이 배열로 오는지.

## 8. 열린 질문 / 후속

- 피치 카드의 (누가·왜/차별점) 자동 채움 vs 템플릿만 — 이번은 **간단 템플릿 + 컨셉 요약 재사용**으로.
- pool 전달: 현재 ideas는 클라이언트 상태 → **클라이언트가 pool을 요청에 실어 보냄**(서버 세션 영속화는 별도).
- 온라인 팀 투표 실시간 동기화는 기존 세션 sync 메커니즘 범위 내에서만(신규 실시간 인프라 없음).
