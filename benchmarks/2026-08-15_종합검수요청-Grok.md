## B. 현재 결정·코드 상태

- **가벼움(ice/keyword) = Gemini-2.5-Flash-Lite** (결정, 코드 반영됨)
- **무거움(analyze/report) = Nemotron-3.5-L 또는 Solar-Pro4** (잠정 — 코드엔 아직 GLM-4.6, 92초·비쌈이라 교체 필요)
- **idea 각도 배정 = 다양성 기반** (특화는 노이즈라 특화배정 안 함)
- **정직 프레임(확정): 분업 = 난이도별 라우팅 + 비용 + 다양성 + 폭넓은 검증(40+모델) + 정직성.** (품질우위·각도특화 아님)
- 코드: registry 라벨동기화, adapter S1(이중과금)수정·kind별 max_tokens·flagship 추론OFF 반영됨.

## C. 남은 문제 (열린 것)

1. **분업 조율 실패** — fanout이 서로 못 봐서 중복·조율 실패(통제실험). → **제안 해법: Map-Reduce(4각도 병렬 → 종합 콜 1개로 병합)**.
2. **무거운작업 벤치 = 사실상 단일심판** (Llama 배열길이 폐기) → 재검증 필요.
3. **미터가 아직 `estimate-mock`** (토큰은 실측, 비용은 목업단가) → 정직성 갭.
4. **registry의 analyze/report = GLM-4.6** → 무거운벤치 반영(Nemotron/Solar) 미완.
5. **보안(이전 검수 잔여):** 무인증 `/api/ai` + 실키 = 비용공격(B1·일일쿼터 미구현), 프롬프트 주입 강화, 출력 XSS.

## D. 도입 결정 (검수 요청 핵심)

검색(NotebookLM fast) 근거로 3가지 도입 여부를 판단했는데, 맞는지 봐달라:

| 대상 | Claude 판단 | 근거 |
|---|---|---|
| **Map-Reduce 조율** | 🟢 **도입** | 통제실험의 "나눌수록↓"를 직접 해결. `index.js` fanout에 종합 단계 추가(작은 슬라이스). |
| **Langfuse** | 🟢 **도입** | 공식 JS 쿠북 존재. 토큰·비용 자동추적(미터 정직화) + Scores API로 A/B 대시보드화 = 원계획 "검증툴" 완성. |
| **LiteLLM** | 🟡 **보류** | OpenRouter가 이미 게이트웨이+폴백, registry가 이미 라우팅 → **지금은 중복**. 다공급사 확장 시 재검토. |

## E. Grok에게 요청

1. **결론 검수:** A~B의 "분업=난이도라우팅+비용+다양성, 품질우위·각도특화 아님"이 원자료와 정직하게 정합한지. 특히 **무거운작업 결론(추론 뒤집힘)이 단일심판인데 얼마나 믿을 수 있나** — 재검증 전 발표 가능 수위.
2. **도입 결정 검수:** Map-Reduce 도입 / Langfuse 도입 / LiteLLM 보류 — 이 3판단이 사업성·정직성·과설계방지(§9) 상 맞는지. 특히 Langfuse 도입 시 "다공급사로 아이디어 원문 분기 → 학습·보관 고지"(설계 §8) 프라이버시와 충돌 없는지.
3. **남은 문제 우선순위:** C의 5개 중 발표·실사용 전 반드시 먼저 할 것 순서. (조율 vs 심판재검증 vs 미터정직화 vs registry교체 vs 보안B1)
4. **놓친 것:** 정직성·보안·통계적으로 우리가 아직 못 본 구멍. 발표에서 "이건 하면 안 된다"는 과장 라인.
